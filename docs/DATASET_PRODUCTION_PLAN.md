# 训练数据生产系统 · 差距诊断与计划（2026-10-09）

> **先说定位差别**：现在是**质量决策系统**（回答"这条数据好不好、为什么丢"），
> 要变成**训练数据生产系统**（回答"给我一个能直接喂给 trainer 的东西"）。
> 这不是加功能，是**产物形态变了** —— 从「报告」变成「数据集制品」。

---

## 一、实测差距：现在的产物不是数据集

| 现在产出（实点`data/processed/`） | 训练系统需要 |
|---|---|
| `cleaned.jsonl`（原始字段，无 schema 契约） | **typed schema** + 显式字段定义与版本 |
| `dropped.jsonl` + `funnel_stats.json` + `report.md` | **manifest**：样本数、token 数、来源谱系、校验和、许可证、版本 |
| 无 tokenizer 处理 | **tokenize + packing**（模型消费的最小单位） |
| 无切分 | **train/val/test 切分 + 泄漏检查** |
| 无打包 | **shard 化**（单文件几百MB 训不动，且无法流式） |
| 无加载接口 | **标准 loader**（`datasets` / `DataLoader` 可直接读） |

**最大的一个发现**：`benchmarks/*/manifest.json` 里**已经有 leakage_check**
（md5_leaks + minhash_leaks 两个字段），也就是说**泄漏检测的能力已经有了，
只是没用在训练数据集的切分上**。这是能直接复用的现成资产。

**第二个发现**：训练侧其实已经跑通了 —— `eval_training_utility.py` 用
`AutoTokenizer.from_pretrained` 真的训了模型（three arms: base / unclean / cleaned）。
但它是自己 `load_corpus()` 读 JSONL，**绕过了任何"数据集"抽象**。
所以缺的正是中间那一层：**JSONL → 数据集 → trainer**。

⚠️ **注意别重复 G1 的坑**：G1 刚翻过"清洗让模型显著更差"（Δ=-0.195，4.46 倍噪声地板）。
做生产系统时**同一批数据会再次被消费**，如果结论仍是负的，
那说明**产出的数据集不该按当前漏斗配方发布** —— 这正是生产系统比决策系统更诚实的地方：
它必须对"这个数据集值不值得训"负责。

## 二、四层缺口（按依赖顺序，不是按重要性）

### 第0 层：**数据集制品规范**（最缺，一切的前提）

现在没有"什么是数据集"的定义。要定下来：

```
datasets/<name>/
  manifest.json# 唯一真相源：n_samples / n_tokens / schema 版本 / 谱系 / 校验和 / 许可
  shards/train-00000.parquet  # 二进制、列式、可流式
  shards/val-00000.parquet
  shards/test-00000.parquet
  splits.json          # 切分 + 泄漏检查结果
  tokens/              # tokenize 后的 uint32 二进制（或直接 Parquet 内）
  README.md            # 这个数据集怎么用、训练什么模型效果如何
```

**关键决策：`manifest` 必须包含"这个数据集用哪个 recipe 训出什么结果"** ——
这是 DataComp 的核心思想，也是本项目现在完全没有的东西。
没有这一项，它就只是"一堆洗过的文本"，不是"训练数据产品"。

### 第 1 层：**tokenize + packing + 切分 + 泄漏检查**
- 中文没有现成 tokenizer 好用：`transformers` 的 gpt2 是英文的
  → 要么换 multilingual/Chinese tokenizer，要么自训（`text_quality_classifier` 已有训练管线可复用）
- packing 把变长文本拼成定长 block，是吞吐量的关键
- 切分必须**先切分再 tokenize**，否则 test 集会泄漏进 train
- 泄漏检查复用 benchmark 里的 md5 + minhash 双检

### 第 2 层：**训练侧闭环**（把 G1 变成流水线的一部分）
- G1 现在是**一次性脚本**（跑一次 15 小时）。生产系统需要**可复跑的 recipe**
- recipe = 数据集版本 + 模型 + 超参 + 结果，落成一份可对比的 run 记录
- 这是"训练数据生产"的完整闭环：**产出 → 训练 → 验证 → 迭代回数据**

### 第 3 层：**规模化**
- 33 万 → 100 万+（现在 Shard 化之后才可能）
- 分布式：这里才轮到 Ray/Spark，且**传输格式改造是前置**（已实测负收益）

## 三、范围与优先级（我的建议）

### ⭐ P0：数据集制品规范 + 一个真实产出的数据集（2-3 天）

**这一层不做，后面全是空中楼阁。**

1. 定义 `DatasetManifest` schema（pydantic 或 dataclass + JSON schema）
2. 写 `build_dataset()`：JSONL → 校验 → 切分 → 去重 → tokenize → packing → shard
3. **用一个现有漏斗跑出一条真实数据集**（建议 finance_news，因为它有 214 条真实
   且有symbol 元数据，可做分层切分）
4. manifest 里必须写清：n_tokens / 谱系（哪个漏斗哪个版本）/ 校验和 / **泄漏检查结果**
5. **用第 4 步的产物真的训一次模型**，把run 结果写回 manifest

**产出**：一个能被`datasets.load_dataset()` 或 DataLoader 直接读、
且 manifest 完整描述自己来历与训练效果的数据集。
**这是"训练数据生产系统"最小的、完整的、可演示的闭环。**

⚠️ 诚实提醒：如果拿现有 33 万跑，tokenize 33 万中文要选tokenizer，
可能比预期慢（要试）。建议先用 finance_news 打通全链路，再上规模。

### P1：训练 recipe 系统（2 天）
把 G1 的逻辑产品化：`recipes/<name>.yaml`（数据集 + 模型 + 超参）→ run 记录
→ 可横向对比多个数据集版本的效果。**这才是"生产"的含义** —— 可迭代、可回溯。

### P2：中文 tokenizer（1-2 天，可与 P0 并行调研）
选型对比（multilingual vs Qwen vs 自训），
**判据要现取**：拿一批真实中文语料测vocab 覆盖率 + 压缩率，
而不是拍脑袋。

### P3：规模化 + 分布式（3 天+）
Shard 化之后才做。这里 Ray 的传输格式改造才有意义（前面已实测它是负收益）。

## 四、需要你拍板

| # | 问题 | 我的建议 | 备选 |
|---|---|---|---|
| 1 | **先做哪个数据集**？ | **finance_news**（214 条真实、带 symbol 元数据、可分层切分、tokenize 快） | text_funnel 33 万（更壮观但更慢）、COCO 图文（要处理图片存储） |

## 五、我不会做的事（写下来）

- 不会造一个"看起来像数据集"的东西（只有 JSONL 改名不算）
- 不会在 manifest 里写没实测过的数字（每项都要有产出脚本）
- 不会假装规模（33 万 vs 15T token，差距继续明写）
- 不会在 P0 完成前动 P3 分布式（地基没有，上面全是空中楼阁）
- 不会动 `Sample`/`Operator` 协议签名与既有 4 个 config（硬约束）

## 六、与外部评审建议的关系

两份评审都建议"Q5 别做分布式、先做单机精做"—— 本计划与之一致，
但**优先级不同**：他们建议先诊断 Q4（误合并）、先做 Q6/Q1/Q3（小修），
而本计划认为**造出真正的数据集制品才是主线**，那些小修可以并入 P0/P1 一起做。

⚠️ 一致的地方：不做分布式去重（现在也不做）、
⚠️ 不一致的地方：**优先级** —— 评审认为先修地基，本计划认为先立"数据集"这个产物形态。
理由：地基的最终检验标准就是"能不能产出可训练的东西"，没有产物形态就没有检验标准。
