# 工程发现日志（面试弹药库）

> 开发过程中的真实现象、排查与抉择，按类归档。每条 = 现象 → 根因/排查 → 决策与理由。
> 面试原则：讲"我发现了什么、怎么定位、为什么这么决策"，不讲"我用了什么 API"。

## 一、数据源与数据质量（最出彩的一类）

### 1. 「数据集存在」≠「可用」：parquet 镜像的 schema 陷阱
- 现象：从 HF 镜像下了 460MB 的 COCO2014 图像 parquet，join COCO-CN 标注时命中率仅 3.5%（理论应 ~16.5%）
- 排查：逐行比对发现 `image_id` 是**数据集自己的自增序号**而非 COCO 官方 id，`image.path` 字段全空——那 3.5% 是小数字 id 的巧合碰撞
- 决策：弃用，换保留原始文件名的 `ali-sh07/COCO-train2014`（命中 1,620 对）
- 话术：「我踩过'镜像数据集字段语义与预期不符'的坑，之后所有外部数据源先验 schema 再谈下载，把教训写进了模块文档防止复发」

### 2. 断连损坏文件：下载必须原子写 + 完整性校验
- 现象：全量下载后 3 张图 PIL 无法解析（UnidentifiedImageError）
- 根因：下载中途断连留下半截文件，重跑时"文件存在即跳过"的幂等逻辑把坏文件当成了品
- 决策：`fetch` 改为先写 `.part` 再原子改名；加 PIL `verify()` 清理存量坏图。**幂等和完整性是两个需求，只做前者会静默产出脏数据**

### 3. 国内网络的镜像工程
- 现象：HF 直连超时、COCO 官方 DNS 不通、hf-mirror 裸请求 403
- 决策：下载链路内建「镜像端点 + 浏览器 UA + 重试 + 幂等」；直连 PyPI 慢一个数量级 → 清华镜像
- 话术：「这不是配环境的小事，是国内数据岗位每天的真实工作面，我的下载器把这些做成了默认行为」

### 4. COCO 自然存在近重复
- 现象：pHash 阈值扫描发现干净集里有大量"误杀"候选——实为同场景连拍等自然近重复
- 决策：评测口径区分「注入脏数据」与「自然重复」；后者被去重是**业务正确**行为
- 话术：「ground truth 本身有局限，我把它变成了评测设计的显式决策而不是假装不存在」

## 二、阈值与算法校准（方法论核心）

### 5. 污染强度与算子阈值是耦合参数，必须联合校准
- 现象：MinHash 阈值 0.5 时召回 100% 但误杀 2.9%；提到 0.7 召回崩到 15%——单调任何一边都无解
- 根因：污染器扰动太强，注入对的 Jaccard 中位数只有 0.61，与"模板句自然相似"（0.5-0.6）区间重叠
- 决策：先改污染强度（8-gram 重复+条件删字，J 提到 0.85±），再定阈值 0.65（召回 94%/误杀 0.7%）
- 话术：「模拟脏数据要么太脏要么太干净都会让校准失真——我把污染强度当成和阈值一起优化的变量」

### 6. pHash 的误杀悬崖
- 现象：阈值 14→16，误杀从 44 跳到 200（非线性的悬崖）
- 决策：定 12（召回 84%/误杀 0.3%），把 `crop_resistant_hash` 列为强裁剪场景的扩展路径
- 话术：「阈值不是拍脑袋的默认值，我扫出整条曲线选拐点，还知道边界外是什么」

### 7. 短文本去重守卫
- 现象：3-gram MinHash 对短 caption（截断类脏数据的典型产物）产生大量虚假碰撞
- 决策：`min_len=8` 以下不参与聚类——「无区分力的信号参与聚类只会制造噪声」

### 8. CLIP 对齐分一石三鸟
- 现象：图文对齐阈值 0.38 除了抓错配（召回 96%），还压住了 NSFW 占位图（0.37-0.39）和刷字文本（p50=0.376）
- 话术：「算子的收益要看它对整个污染分布的作用，不是只看设计靶子」

## 三、漏斗架构（阶段顺序的涌现现象）

### 9. 阶段顺序会"抢功"
- 现象：只改 caption 不动图的注入（错配/低质文本）全被上游 md5 拦截（图像字节相同），L2 到位后漏斗内只掉 5 条
- 决策：算子级 P/R 评测必须在**全量脏集上独立跑**，漏斗数字只用于端到端收益
- 话术：「管道指标和组件指标会互相掩盖，评测体系必须同时有两个视角」——这是很多真实数据团队的盲区

### 10. 低分辨率注入被模糊度算子抓走
- 现象：`low_resolution`（下采样后放大回原尺寸）分辨率不变，但高频被摧毁 → Laplacian 方差暴跌，被 `blur` 算子全量召回
- 话术：「脏数据的'标签'和它的'可检测特征'是两回事，算子按特征工作不按标签工作」

### 11. 三层成本分级的实证
- 结构：L1 规则（毫秒）→ 哈希去重（秒）→ L2 模型（GPU 分钟级），便宜算子先把 2,106 缩到 1,607 再上 CLIP
- 话术：「JD 里'成本意识'的落地：不只是分层本身，而是每层的阈值都有召回-误杀-成本三角的显式取舍」

## 四、依赖与环境（踩坑密度最高的区域）

### 12. transformers 5.x 的 torch 版本墙
- 现象：transformers 5.4 拒绝在 torch<2.6 上 torch.load（CVE-2025-32434），而 cu121 轮子最高 2.5.1
- 决策链：先降 transformers 4.57（小下载）而不是升 torch 2.6+（2.5GB）——**先评估约束的方向，别顺着报错走**

### 13. 官方仓库只有 .bin 权重
- 决策：本地 `torch.load(weights_only=True)` 读官方 bin → 转 safetensors 存本地目录，编码器优先用本地、回落在线
- 话术：「在版本墙和 2.5GB 下载之间找到了第三条路：格式转换，一次性成本」

### 14. transformers 4.57 中文 CLIP 回归 bug
- 现象：`get_text_features` 崩溃：文本塔 `add_pooling_layer=False` 却读 `pooler_output`
- 排查：对照官方权重键名发现根本没有 pooler 参数 → 官方实现是 CLS token 直接过 text_projection
- 决策：编码器绕过 `get_text_features` 手写正确前向，注释写明原因和上游 bug
- 话术：「读上游源码和权重结构定位了 transformers 的回归 bug， workaround 有据可查」

### 15. fastapi/httpx 断代不兼容
- 现象：fastapi 0.109 的 TestClient 给 httpx 传已删除的 `app=` 参数 → TypeError
- 决策：升级 fastapi 到 0.141（连带 pydantic 2 全兼容），而非锁旧 httpx
- 原则：**依赖组合里选"向新"的一侧，锁旧会累积技术债**

### 16. Pillow 12 删了 `Image.isImageType`
- 决策：`isinstance(image, Image.Image)`。教训：依赖大版本升级后先扫废弃 API 列表

### 17. opencv 5.x 强制 numpy≥2 vs torch 按 numpy 1.x 编译
- 决策：requirements 里同时钉住 `numpy<2` 和 `opencv-python<5`，并写明原因注释
- 话术：「版本约束不是玄学，是依赖图的显式推理」

## 五、测试工程

### 18. 时钟耦合的 flaky 测试
- 现象：stale 检测测试单跑绿、全量偶发红
- 根因：断言依赖 `datetime.now()` 与文件 mtime 的相对关系，系统负载下时钟粒度踩边
- 决策：固定 `built_at` + 显式 epoch 控制 mtime，与真实时钟完全解耦
- 原则：**时间语义的逻辑测试永不依赖真实时钟**

### 19. JPEG 有损让像素级断言失配
- 现象：纯色 (160,80,120) 存 JPEG 读回变 (160,79,120)，假编码器颜色字典 KeyError
- 决策：夹具改 PNG。原则：像素级断言永远用无损格式

### 20. 原地修改与别名陷阱
- 现象：断言"改写生效"永远失败——`out IS src`，比较的是同一个被改过的对象
- 决策：断言前快照不可变原始值（字符串）；夹具不复用被污染过的样本对象
- 话术：「Python 引用语义在数据管道里天天咬人，我把项目约定写进了测试注释」

## 六、产品与检索（D1-D2 手测发现）

### 21. 脏数据对检索的污染有直接证据
- 现象：查询"一只狗在草地上奔跑"：净索引 top3 全是相关干净结果；脏索引 top3 里 2 条脏数据、**模糊图排第一**（错配的斗牛犬 caption 与查询相似度高）
- 机制：①重复样本挤占 top-K 名额 ②错配对让"文不对题"的图抢排名
- 话术：「清洗的价值不用嘴说，一条查询两个索引的对比就是证据」——D3 把它量化成 Recall@K/MRR

### 22. 静态资源用精确文件白名单而非目录前缀
- 抉择：只放行索引 store 登记过的文件 → 路径穿越天然无效；代价是新增文件需重建索引才可见
- 话术：「安全边界选了更窄的那个，代价显式 documented」

### 23. 惰性加载 + 单例 + 向量缓存的收益实测
- 数字：首次查询 7.6s（模型加载）→ 热查询 67ms；图像向量跨算子复用（clip_alignment 与 semantic_dedup 不重复编码）
- 话术：「推理服务的成本结构：把一次性成本和每请求成本分开优化」

## 七、流程与方法（AI Coding 协议本身）

### 24. 文档驱动的确认门改变了 bug 分布
- 现象：协议落地后（设计表→原子任务→层间确认），回归类返工显著减少；错误集中在"环境适配"而非"设计漂移"
- 话术：「把 AI 当执行者时，设计门和测试证据比代码审查更有效——我全程用 pytest 输出做验收物」

### 25. 已知未解决的问题（主动暴露）
- phash t=12 漏掉的 5 个强裁剪样本（crop_resistant_hash 待接）
- minhash LSH 概率性漏检（~6% 的边界 Jaccard 对）
- held-out 查询仅 119 条（8%），扩种子集后统计功效更强
- 话术：「知道系统边界在哪，比系统本身更能体现工程成熟度」

### 26. 灵魂实验的数字与"头部挤压"效应
- 数字：同查询集同目标，清洗使 Recall@1 0.459→0.556（相对+21%）、MRR +7.1pp、R@10 +2.7pp
- 洞察：**污染伤害集中在头部名次**（R@1 掉 9.7pp vs R@10 仅 2.7pp）——重复/错配样本
  挤占的是 top 位置而非长尾；对"第一名正确性"敏感的业务（推荐首位、RAG 引用）
  清洗的边际收益远大于平均指标所示
- 话术：「我不只报平均指标，还看了退化的名次结构——头部挤压机制直接指向
  哪些业务场景最该投资清洗」

### 27. 评测设计的自检：自检索偏置检验
- 设计担忧：查询=入库 caption 的自检索偏乐观（文本向量完全相同）
- 结果：held-out 查询（未参与索引构建）与 self 查询的退化幅度一致（9.3 vs 9.7pp）
  → 偏置存在（绝对值）但不影响对比结论（差分）
- 话术：「评测里每个方法论风险我都设计了对照检验，不是跑出数字就完了」

### 28. held-out 查询绝对值反而更高
- 现象：held_out R@1=0.580 > self 0.554——违反直觉
- 解释：extra_captions 是人工撰写的另一句描述，比部分干瘪的 primary caption 更自然丰富
- 话术：「反直觉的数据点往往藏着数据本身的特性，追一句为什么比忽略它值钱」

## 八、D4/Week4 阶段新发现（算子评测、消融、采样）

### 29. "md5 拦截 caption 注入"从猜想变成实测
- 此前（#9）从机制推断：只改 caption 不动图的注入会被 md5 全拦。独立评测实证：
  md5 单算子丢 220 条 = 精确重复 58 + 错配/低质文本/近重复文本等共享图像字节的注入
- 话术：「我对管道行为的推断都会找机会用独立评测验证，这次推断和实测完全吻合」

### 30. 分辨率算子召回 0%——脏数据的标签与可检测特征错位（定量版）
- resolution 独立评测召回 0%：low_resolution 注入是"下采样后放大回原尺寸"，
  分辨率维度不变、高频被摧毁——100% 被 blur 算子按"模糊特征"抓走
- 话术：「#10 的定性观察在算子矩阵里变成了精确数字：标签是 low_resolution，
  可检测特征是模糊。清洗算子按特征工作，不按标注工作」

### 31. 消融的方法论教训：边际贡献 ≠ 重要性
- 现象：逐个移除算子，ΔR@1 全部为 0——"没有单个算子是 load-bearing"
- 原因：算子间强冗余（如 blur 的靶子同时能被 phash/minhash 兜底）；
  且单个算子只贡献 4~17 条样本，撼动不了 119 查询的 top-1
- 解法：**分组消融**——移除去重四件套，R@1 -0.017（246 条重复回流），唯一显著组
- 话术：「leave-one-out 在冗余系统里会得出'一切都没用'的错误结论；
  我改用分组消融才看到真实贡献结构。这也是为什么真实团队做消融要设计粒度」

### 32. 分层采样的收益与一个诚实反例
- 收益：固定预算下分层采样 R@1 全面领先（budget=1000 时 0.353→0.437，+24%）
- 反例：budget=800 时分层 R@10（0.445）反而略低于随机（0.454）——预算极紧时
  高质量层配额挤占了类目覆盖，top-10 的长尾召回受损
- 话术：「采样策略不是单调占优，预算-覆盖-质量三者在极端预算下会冲突；
  我的实验把冲突点也画出来了」

### 33. 零重编码评测：让消融实验便宜到可以反复跑
- 技巧：全部消融配置共用 dirty_raw 的全量索引排名，按存活集过滤即得子集排名
  （IndexFlatIP 精确检索的子集序保持不变），12 个配置零 GPU 重编码
- 话术：「实验成本决定了迭代次数——把 12 次消融从'每次几分钟 GPU'降到
  '秒级过滤'，才敢做分组消融这种更细的实验设计」

### 34. 已知口径差异（面试要能答上）
- 消融报告 held_out=120 条（全集 1620 干净样本上构造）vs D3 报告 119 条
  （漏斗存活 1585 上构造）：前者保证跨消融配置查询集恒定，后者保证目标在净索引可达。
  两个口径各自服务于实验目的，结论互不受影响，但数字不能混着引用

## 九、Phase 2 阶段发现（检测器迭代 / 质量门 / 阈值）

### 35. 检测器四轮迭代：一次教科书级的"负结果驱动设计修正"
- R1（四维全留出）：testA 97.8% / testB 43.2%——水印召回 5.8%，模型背下了平铺图案
- R2（增广+可见性校准）：testA 99.6% / testB 反而 36.6%——增广只提升了记忆
- **量化破案**：梯度能量比 A 组水印 1.33 vs B 组角落水印 0.95——角落小字在
  224px 下低于自然图像噪声底，**探针本身不可检**，不是模型不行
- R3（banner 探针）：水印召回仍 0%——布局作为留出维度=要求零样本迁移到
  未见任务结构，协议过于激进
- R4（定稿协议）：训练组含布局模板多样性（tiled+banner），泛化组留出
  **风格参数**（字体/文本/透明度）→ testA 98.2% / **testB 87.3%（水印 88%）**
- 话术：「合成数据训练检测器的循环论证质疑，我用『风格错开+量化探针公平性』
  双重设计回应；三次失败各自量化归因，最后落在与真实检测器训练范式一致的
  协议上——布局是训练数据设计，风格才是泛化维度」

### 36. 检测阈值的 softmax 陷阱
- 现象：min=0.90（脏类概率>0.10 即丢）在合成测试集上干净召回 97.5%，
  在全量真实集上干净误杀却达 16.9%
- 根因：softmax 分数分布长尾——干净图 p10=0.859，阈值拍在分布密集区
- 修正：全量脏集扫描后定 min=0.30 → 主靶召回 100% / 误杀 0.8%
- 话术：「合成测试集的分数分布不能代表真实分布，阈值必须在部署分布上校准」

### 37. 实时质量门：在线判定与离线漏斗同源
- 设计：/api/ingest 单端点返回 质量分 + flags + 三层增量判重 + accept 决策；
  算子与阈值直接复用漏斗 YAML——在线离线口径一致的刻意设计
- 增量去重：md5 字典 + pHash 线性扫 + MinHash-LSH 原生 insert/query，
  "查-判-插"一次完成；十万级以上 pHash 需换分桶（已注明扩展路径）

### 38. 测试夹具的三次"纯色图陷阱"
- pHash 增量判重测试：纯色图无论颜色多不同全部判定近重复（DCT 低频无结构）
- 质量门测试：纯色图 Laplacian 方差≈0 被 blur 阈值正确拦截
- 结论：**涉及图像特征的测试夹具必须用结构化图（渐变+形状）**，
  已沉淀为测试工具函数

### 39. 训练级直接验证：脏数据让学出来的模型更差
- 实验：同一 Chinese-CLIP 基座，等步数（100 步）分别在干净集（1585 对）与
  脏集（2106 对）微调，同一查询集评测
- 结果：**干净微调 R@1=0.688 / MRR=0.791 vs 脏微调 R@1=0.636 / MRR=0.748**
  （差 5.2pp / 相对 8%）——清洗的价值第一次在"模型训练效果"层面被直接证明，
  不再只是检索代理指标
- 方法学互证：base（未微调）R@1=0.556 与 D3 独立实验的 clean_v2 完全一致
- 话术：「检索是代理，训练是金标准——我两级都做了，且两套实验的基线数字
  相互对得上，说明评测体系自洽」

### 43. 成本核算的两个测量陷阱与缓存红利

- 话术：「我按『每百万样本耗时 + 相对倍数 + 召回』给算子排性价比，

## V2 β：文本语料实例（2026-08）

### 44. JSONL 里的隐形换行：U+2028 撕碎 splitlines
- 现象：去重基准加载语料报 `JSONDecodeError: Unterminated string`，
  但逐行 `for line in f` 校验 0 坏行——两种读法结论矛盾
- 根因：`str.splitlines()` 除 `\n` 外还按 U+2028/U+2029/`\x85` 等
  Unicode 行分隔符切分，维基正文真实包含这些字符；JSONL 是 `\n`
  分隔协议（字符串内换行必已转义），按字面 `split("\n")` 永远安全
- 决策：所有 JSONL 读取点统一 `read_text().split("\n")`；教训是
  「行协议的行由协议定义，不由语言工具函数定义」
- 话术：「一个 splitlines 的默认行为差异，让我学会了区分『文本的行』
  和『协议的行』——校验和实现必须走同一条代码路径，否则校验是假的」

### 45. 模板化语料簇 vs MinHash-LSH：参数即语义
- 现象：30 万维基语料去重「误杀」5.8 万/10 万，精确重复召回反而只有
  0.55——算法大面积失常
- 根因：语料里有海量同模板条目簇（如上千个只换人名的开国少将条目），
  它们在 600 字节前缀的 Jaccard 视角下真实相似度 ≈0.75-0.8：合并它们
  不是误杀，是 Jaccard 去重的固有语义。真正的事故是这些家族把 LSH 桶
  撑破（>max_bucket 整桶跳过），桶内真重复被连带牺牲
- 决策：三招——(1) 签名完全相同的样本在分桶前无条件预聚类（精确重复
  不受跳桶影响）；(2) 用 LSH 捕获公式 1-(1-J^rows)^bands 重调参数：
  rows 6→10 让家族共桶率从 0.18 降到 0.056（桶回可复核规模），再加
  band 到 8 把 J≈0.9 捕获率拉回 0.95；(3) 指标改名 `non_injected_merged`
  并在报告写明口径——召回只对注入样本结算
- 数字：10 万档 exact 召回 1.0 / near 召回 0.97 / 21 秒 / RSS 825MB；
  30 万档 60 秒（参考实现逐文档签名是小时级）
- 话术：「基准跑出 5.8 万误杀，追查后发现一半是维基模板条目簇——
  这教会我『去重语义和语料构成是耦合的』，LSH 的 rows/bands 不是
  性能旋钮，是捕获曲线的中心位置」

### 46. union-find 的合并方向决定「先到先保留」是不是真的
- 现象：LSH 参数修完后 near 召回仍只有 0.42；漏检对明明共桶（桶大小
  =2，只有它们俩）且签名一致率 0.91 远超阈值——合并发生了，召回却
  不涨
- 根因：`parent[rx] = ry` 把较大索引一侧的根设为簇代表；注入样本永远
  在列表尾部（大索引），于是合并后**注入副本当上簇代表被保留**，
  真源文档被丢——pair 合并了，但 `duplicate_of` 记录的是源 id，
  召回结算时注入 id 不在集合里。「先到先保留」实际是「随机的那个」
- 决策：`parent[max(rx,ry)] = min(rx,ry)`，让合并方向保证簇代表 = 
  最先出现的样本；补了不变量测试（duplicate_of 的值必须在输入顺序
  上先于键）
- 话术：「union-find 不写 union-by-rank 时，谁当代表是合并方向决定的
  ——一个没有断言的约定等于没有约定。这个 bug 让召回从 0.42 到 0.97，
  是我吃过最隐蔽的一次『结果对但语义错』」

### 47. .bin 权重墙第二撞：把补丁升级成入口
- 现象：GPT-2 zh 微调一启动就 ValueError（CVE-2025-32434 要求
  torch≥2.6 或 safetensors）——和当初 Chinese-CLIP 一模一样的墙
- 根因：uer/gpt2-chinese-cluecorpussmall 只有 pytorch_model.bin；
  transformers 4.57 拒绝在 torch 2.5 上 torch.load
- 决策：不复制 CLIP 的转换脚本，而是抽 `ensure_local_gpt2()` 单一
  入口（本地 safetensors 就绪→直接用；缓存有 .bin→转；否则报错
  指路），perplexity 算子与微调脚本共用。转换时又踩一层：
  safetensors 0.7 的 save_model 元数据不含 format:pt 会被拒载，
  必须 save_file + 显式 metadata；tied 权重先 clone 解共享内存
- 话术：「同一个坑摔两次说明补丁位置不对——第二次我把补丁做成了
  加载入口本身，顺带把『模型资产本地化』变成了可复用的模块」

### 48. 污染器和算子各自单测全绿，却互相打不中
- 现象：β 验收测试里 paragraph_repeat 注入的脏数据，靶子算子
  line_repetition 根本抓不到——但两者的单测都是绿的
- 根因：污染器把重复片段**行内拼接**（seg*3 变成一行），算子数的
  是**重复行**——行内重复它看不见。同理 whitespace_pad 往内部插
  空白（strip 后长度不减）、插在尾部（下游算子 strip 无声剥离），
  doc_length 都接不住。单元测试的夹具是手写的，天然和实现同构，
  测不出「对靶」问题
- 决策：验收测试必须用真实污染器产脏 + 真实漏斗消费，逐类型断言
  拦截阶段；污染器按「可被靶子算子观测的损伤」重写语义（整行复制、
  替换式内部空白块）
- 话术：「红绿测试防的是回归，防不了『两边的假设各自自洽但互相
  不认识』——集成测试的价值在跨模块的语义对齐，这是我给 ground
  truth 方法论补上的最后一环」

### 49. 造测试数据被去重连续打脸三次：模板即重复
- 现象：β 验收测试的 28 篇「干净」文档三次被 text_minhash 大量合并，
  我三次怀疑去重有 bug，三次都是测试数据的错：句池周期碰撞（第 i 与
  第 i+8 篇三句全同）、同骨架模板（只换槽位数字）、共享连接词骨架
  ——字节 4-gram 视角下它们的真实 Jaccard 高达 0.6-0.9
- 根因：短文本的 shingle 集合里，模板骨架贡献的 gram 占绝对多数；
  人眼觉得「只差个序号」，在去重眼里就是近重复。这与 #45 的维基
  模板条目簇是同一个事实的两面
- 决策：手写 28 篇真实互异文本；先算两两真实 J（实测 max 0.047）
  再跑测试。把「先验证造数据的分布，再写断言」固化成习惯
- 话术：「我被自己的测试数据骗了三次，也把这个教训讲成了产品能力：
  模板化内容就该被去重合并——维基语料的模板簇实验证明系统是对的」

### 50. 阴性对照的价值：微调实验首跑 ppl 差 0.4% 的三层归因
- 现象：干净 vs 脏语料微调 GPT-2 zh，held-out ppl 7.18 vs 7.21，
  差 0.4%（噪声级），验收线是 >5%——实验「成功跑完」但结论阴性
- 根因（拆开是三层）：
  (1) 剂量：dirty_rate=0.10，两臂 90% 文档完全相同，处理强度先天不足；
  (2) 损伤集掺假：旧 mojibake 是 gbk 编码再按 utf-8 解码，纯中文的
  gbk 字节几乎全被 `errors="ignore"` 丢弃 → 空串走 `text[:50]` 兜底
  = 温和截断；truncate 也只是「短」而语言分布无损——四种损伤里
  只剩段落复读真正有害，有效剂量 ≈ 3% 文档；
  (3) 长度混杂：损伤文档更短，等步数训练时按 token 算的污染占比
  比文档占比再打对折
- 决策：损伤集按「对语言模型真有害且与清洗算子同靶」重造——乱码改成
  现实中最常见的 UTF-8 字节流被按 GBK 误解码（合法汉字、语义全毁），
  新增重复字符插入（char_repetition 算子的靶），剂量提至 1.0 做干净
  A/B。首跑数字留档为灵敏度下界：10% 轻度污染在此规模不可测
- 话术：「实验跑完不等于实验成功。0.4% 的阴性结果逼我把『脏』拆成
  剂量、损伤类型、长度混杂三层去归因——阴性对照教会我的，比一次
  顺利的阳性更多：效应量是设计出来的，不是跑出来的」

### 51. 对外发布的包，CI 却从来没测过它
- 现象：`curation-eval` 已升级为「协议与 SDK 的单一来源」、README 对外
  宣称 pip 可装，但 CI 的 `pytest -v` 只跑主仓库 129 项——包的 29 项测试
  **从未在 CI 上执行过**；`ruff check src tests scripts dags` 同样不含
  `packages/`。也就是说产品化核心在 CI 上是零门禁裸奔的
- 根因：`pyproject.toml` 的 `testpaths = ["tests"]` 是**白名单**而非发现
  机制——新增顶层目录（packages/）时不会自动纳入，而包是 α 阶段才加进来的，
  CI 配置没跟着演进。lint 范围同理是手工列举
- 决策：CI 显式加一步 `pytest packages/curation-eval/tests`（**不改 testpaths**
  ——避免改变本地 `pytest` 默认行为影响既有习惯），ruff 两个命令的范围补
  `packages`；同时把 ruff **pin 到 0.15.7**（与本机开发版本一致）
- 为什么必须 pin：`ruff format` 的规则随版本漂移。实测本机 venv 是 0.16.3、
  系统（日常用的）是 0.15.7，两者对同一批 β 代码都判合规，但**只要漂一次就
  会出现「本地绿、CI 红」的幽灵失败**——这类失败最难排查，因为它与本次改动无关。
  门禁工具自身的版本，和被测代码一样需要锁定
- 数字：改造前包侧 29 测试 + 全部 lint 在 CI 上零覆盖；改造后 CI 门禁覆盖
  158 测试 + 106 个文件的 lint/format
- 话术：「我对外说这是个可复用的协议包，但 CI 压根不测它——**宣称和保证是
  两回事**。补门禁时我顺手把 ruff 版本也 pin 住了：一个会自己漂移的门禁，
  它的『绿』是没有意义的」

### 52. Git Bash 把 PYTHONPATH 转成了 `C:\c\Users\...`
- 现象：显式 `export PYTHONPATH="C:/Users/.../site-packages"` 后仍
  `ModuleNotFoundError`；打印 `sys.path` 发现路径变成 `C:\c\Users\...`
  ——盘符被当成了一层目录
- 根因：MSYS2 对形如 `/c/...` 和 `C:/...` 的参数都会做 POSIX→Windows 路径
  转换，拼接时多出一层 `c`。这不是 Python 的问题，是 Git Bash 的
  **参数重写**发生在 Python 启动之前
- 决策：`export MSYS_NO_PATHCONV=1` 之后再 export 正斜杠 Windows 路径即可。
  附带一个更隐蔽的点：editable 安装的 `.pth` 文件**只在目录被当作 site 目录
  处理时才解析**，用 PYTHONPATH 把 site-packages 挂进去时 pth 不生效——
  必须直接把包源码目录（`packages/curation-eval/src`）加进 PYTHONPATH
- 话术：「环境问题的排查顺序是：先看工具实际收到了什么参数，再看参数意味着
  什么。我以为是 Python 的 site 机制坏了，实际是 shell 在 Python 之前
  就把路径改写了」

### 53. Ray 化三日谈：worker 导入、map_batches 协议三连、以及「分布式≠更快」
- 现象一：spike 里算子在 driver 上跑得好好的，一到 ray worker 就
  ModuleNotFoundError——driver 的 `sys.path.insert` 不会传播给 worker
  进程；测试里更隐蔽：toy 算子类定义在 test 模块，cloudpickle 对
  「有模块名的类」按引用序列化，worker 侧 `import test_ray_executor`
  直接死
- 现象二：map_batches 返回值协议三连拒：裸 list 不允许（ray≥2.5）→
  dict 值必须是 list/ndarray（标量 int 都不行）→ 各列必须等长（它们是
  输出块的 column，不是普通字典）——最终定下「对象列 + 等长 tag 列」
  协议；take_all 取回还是行级 dict（"item" 对应单个 Sample），与直觉相反
- 现象三：2 万文档单样本算子，本地 0.33s / ray 11.7s——慢 35 倍
- 根因：前两件事的共同根源是 ray.data 为表格数据设计，Python 对象是
  二等公民（pyarrow 列装不下就整列 pickle 兜底）；慢则是调度与序列化
  开销——分布式执行器买的是横向扩展能力，不是单机提速
- 决策：(1) 传输协议在 ray_executor.py 模块注释里钉死成文档；(2) 批量
  算子语义抽 `run_batch_mixed_modality()` 共享函数，Local/Ray 两个执行器
  消费同一份实现（等价性从「测出来的」升级为「构造出来的」）；(3) 等价
  口径 = kept 集按 id 相等 + 每级 StageStat 相等 + 逐 id 分数相等，行序
  不承诺；(4) ray 测试 importorskip——CI 不装 ray 自动跳过，零依赖路径
  保持干净
- 话术：「把漏斗搬上 Ray 的三天，我写的不是分布式代码，是两套运行时
  之间的『语义翻译层』——最后真正保证正确性的设计，是把批量算子的
  语义抽成两个执行器共用的一个函数：等价性不该靠测试断言祈祷，该靠
  让两边根本没有各自的可能性」

### 54. instruct 模型裸喂 = 78% 解析失败：chat template 不是可选项
- 现象：judge 首跑 600 次调用，468 次（78%）解析不出 JSON、平均延迟
  17.2s；冒烟单测时同模型却能正常对答
- 根因：serve_judge 把 prompt 直接喂给 model.generate，**没套
  tokenizer.apply_chat_template**。instruct 模型的「指令遵循」是训练在
  模板格式上的——不进模板，它把指令当续写素材自由发挥（输出不是 JSON），
  而且不吐 EOS，拖满 max_new_tokens 才停（17s 延迟的来源）
- 决策：套模板 + add_generation_prompt=True；冒烟验证输出合法 JSON 后
  重跑。教训泛化：调 instruct 模型，「能对话」和「守格式」是两件事，
  格式契约靠模板 + 解析兜底双保险（解析失败→None 保留不评判，所以
  坏输出只是掉评测覆盖，不会误杀数据——失败语义设计在这里兜底）
- 话术：「同一个模型、同一段 prompt，套不套 chat template 是 78% 解析
  失败和零失败的差别。我更满意的是失败语义的兜底：judge 疯了的时候
  漏斗没有死，只是少了 78% 的覆盖——先想好『它坏了会怎样』，调试时
  就不用祈祷」

### 55. 阈值扫描救不了没有信号的 judge：一个诚实的阴性验收
- 现象：0.5B 判官在 min=0.5 只丢 3/600，P/R=0.67/0.01，κ=0.013——
  但按 α 的经验「分数压在高位是阈值没校准」，有理由怀疑换个阈值就好
- 决策：先做 κ(t) 全阈值域扫描再下结论——结果 κ 在 0.30→0.95 十个
  工作点全部平坦在 ±0.015：不是阈值问题，是 0.5B 对「段落复读/广告
  注入」的判分与脏净标签**零相关**
- 结论：这个阴性是 δ 阶段最有价值的产出——(1) kappa 协议证明了「不能
  因为模型能说话就让它当 judge」；(2) 判定链路本身全工作（解析率 70%、
  确定性抽样、skip 语义），换 7B+/云端 API 只改 base_url；(3) 与 α 的
  阈值校准形成方法论闭环：α 证明了「阈值要扫描」，δ 证明了「扫描只能
  救有信号的曲线，救不了平的」
- 话术：「如果我不跑 kappa 直接上线，这是个看起来能用的随机数生成器。
  阴性结果花了我两轮实验，但它把『LLM-judge』从一个信仰变成了一个
  有准入门槛的工程决策——这正是评测框架存在的意义」

### 56. git push 无输出挂死：两个故障长一个样，但成因毫无关系
- 现象：`git push` 光标卡住无任何输出，直到被 timeout 杀掉（exit 124）。
  前一轮已修过 SSL 证书墙（`http.sslBackend=schannel`），于是惯性怀疑
  又是网络，反复重试半小时无果
- 根因：三个认知错误叠在一起——
  1. **把"无输出"当成"网络慢"**。实际上 `git ls-remote origin main` 秒回，
     说明网络与 SSL 都是好的；秒回 vs 挂死这一秒就能区分是凭据还是网络
  2. **不知道 `-c credential.helper=X` 是追加不是替换**。system 层的
     `helper-selector` 仍排第一先执行，所以单加 `-c credential.helper=wincred`
     看起来"修了但没用"
  3. **不知道取不到凭据会退化成终端交互**。helper-selector 拿不到凭据后，
     git 回退到终端询问 username/password，非交互会话 stdin 无输入 → 永久阻塞
- 决策：不碰 system 层（它在 WorkBuddy 内置 PortableGit 目录里，改了影响
  面不可控），改在 **global 层用空值重置**——`git config --global
  credential.helper ""` 然后 `--add credential.helper wincred`。空值会清空
  已累积的助手列表（含 system 那条），这是唯一不需要管理员权限的覆盖手段
- 教训泛化：**诊断顺序应该按"能否被一秒证伪"排**。SSL 故障会明确报错，
  凭据挂起什么都不说——先跑 `ls-remote` 用一秒排除掉整个网络分支，剩下
  的才是凭据。同理，任何"改了配置没生效"的场合，先确认这个配置项是
  **覆盖语义还是追加语义**（git 的 multi-valued 配置、PATH、LD_LIBRARY_PATH
  都是追加），这一条能省掉大量"我明明改了"的困惑
- 话术：「两个故障都是 push 失败，一个报错一个沉默。报错的那个我半小时
  修好了，沉默的那个我重试了半小时——因为我一直在用修前一个的思路修后
  一个。真正的转折点是我花一秒跑了 ls-remote 发现网络是通的，那一秒把
  搜索空间砍掉一半。之后又踩了『-c 是追加不是替换』，所以最终修法是在
  global 层用空值先重置列表」

### 57. 合成测试图像的两连败：phash 眼里，噪声图和单频光栅都长得一样
- 现象：给「图像漏斗 × Ray 等价性」测试造 10 张"互不相同"的图 + 若干重复，
  两版构图全失败——v1 随机噪声纹理：所有图互相判为重复（16 张塌成 3 簇）；
  v2 不同频率条纹光栅：还是互相判为重复（11 个标记）
- 根因：phash = 32x32 resize + DCT 左上 8x8 低频块 + 中位数阈值。
  1) 随机噪声的能量均匀铺满全频段，低频 8x8 块里全是零附近的抖动，
     中位数阈值在噪声里翻转 → hash 近似随机但**幅度极小**，图与图塌缩；
     2) 单频光栅的能量集中在一个 DCT bin，64bit hash 只有 1-2 个 bit
     有意义 → 频率不同的两张图只差 2-4 bit，远小于阈值 12
  3) 正确构图：**有低频结构的随机图案**——8x8 随机灰度块放大到 64x64，
     其低频块就是一个随机 64bit 向量，图与图距离 ~32bit。再**测试内
     自校验**：换种子直到两两距离 ≥16（> 阈值 12，留出近重复 2px 扰动
     的余量），100 个种子内必中
- 教训泛化：给感知算法造测试数据，必须先弄清它"看"什么。phash 只看
  低频结构，那测试图就要在低频上有受控差异；而"受控"要靠测试内断言
  构图参数本身（自校验种子），不能靠"我觉得这样应该不同"
- 话术：「我造测试图两连败——噪声图在 phash 眼里全都一样，换成不同
  频率的条纹还是全都一样，但原因相反：前者低频没信息，后者信息太集中。
  最后用 8x8 随机块拼图并让测试自己验证两两距离够远才通过。教训是给
  感知算法造数据前先读它的特征提取代码，别用肉眼判断"明显不同」

### 58. 训练/推理协议错位：裸 prompt 练，模板 prompt 考
- 现象：LoRA 判官首训 loss 收敛正常（2.4→1.9），推理却 κ=-0.18，比通用
  模型还差；诊断发现模型在模板 prompt 下输出单个干净 JSON，在裸 prompt
  下连发多份——训练/推理的输入格式根本不是同一个分布
- 根因：SFT 数据拼接用了裸 prompt 续写式，而推理走 apply_chat_template
  ——instruct 模型的行为绑定在模板分布上（笔记 #54 的姊妹篇：#54 是
  「不套模板推理会崩」，#58 是「不套模板训练会学错」）
- 决策：训练侧 batches() 同样 apply_chat_template——「同协议位」从文档
  口号变成逐 token 对齐的代码事实
- 话术：「我给产品写的卖点是『微调判官是同一协议位的即插即用替换』，
  结果第一个打脸的就是我自己：卖点是协议一致，实现里训练和推理各说各话」

### 59. completion 在窗外：loss 正常，任务没学
- 现象：v2 修正模板后 κ 仍≈0；loss 2.5→1.9 收敛曲线漂亮，仿佛一切正常
- 根因（决定性 bug）：新闻正文 ~1500 token，训练窗口 384+48——右截断后
  **completion（JSON 判分）几乎永远落在窗口外**，loss 上模型实际学的是
  「续写文章」而非「输出判分」。打分直方图实锤：clean 与 dirty 都是
  双峰（两组各有半数被打 1 分）——判别信号根本没进损失
- 决策：prompt 按 completion 长度预留预算截断（completion 永不截）；
  训练窗口 640 与推理 640 对齐。修正后第一个 epoch loss 就从 2.5 级
  跌到 0.69，最终 0.15；冻结 benchmark 上 κ 从 -0.18 → **+0.56**，
  解析率 59% → 100%
- 为什么 loss 曲线骗过了我：续写新闻的 loss 和学判分的 loss 数值量级
  相当，单看曲线完全「健康」——**任务被静默替换时，唯一的症状是下游
  指标，不是训练指标**
- 话术：「这是全项目最贵的一课：两次训练 80 分钟 GPU 买来的认知是——
  loss 是模型在学『某个』任务的证明，不是在学『你要的』任务的证明。
  判据永远是冻结 benchmark 上的下游数字，这正是我们花大力气先造
  benchmark 的原因——没有它，这个 bug 会永远藏在一条好看的 loss 曲线里」

### 60. DPO 的梯度流向由「chosen/rejected 的差异面」决定
- 现象：偏好判官首轮 DPO train loss 收敛到 0.086（看起来学得极好），
  冻结 benchmark 上命中率却双双 ~0.5（随机），且 PA/PB 两个判官行为
  完全一致（分歧率 1.7%）——两个「偏好」训出了同一个没有偏好的模型
- 根因：chosen 与 rejected 的 completion 除了甲/乙字母，reason 文本也
  不同（模板化短语）。DPO 的梯度沿两序列的差异面分布——reason 模板
  token 量大、易学，字母判别 token 难学，梯度全被前者吸收。loss 0.086
  度量的是「复现模板 + 背模板答案」的能力，与「读内容做判别」无关
- 决策：chosen/rejected 改成**最小对**——唯一差异是甲/乙字母（reason
  固定同文），梯度被逼着流经判别 token。重训后命中率 0.50→0.93/0.87，
  分歧率 1.7%→78.3%
- 话术：「DPO 不是『给了正负例就会学对』——负例与正例在哪里不同，
  模型就在哪里学。我的第一批数据里，正负例最显著的不同是废话模板，
  于是模型成了一位背模板的裁判；把差异收窄到一个字母，它才睁开眼
  去读内容」
- 关联：#59 的「completion 在窗外」是同一族问题——训练信号被无关
  事物稀释/截断，症状都在下游指标，不在 loss

### 61. 解析失败伪装成「模型学崩」：先修评测器再下结论
- 现象：DPO 判官首轮评测命中率 PB/main=0.033，看似灾难性反向；
  但手测同 adapter 同题却答对——两处观测矛盾
- 根因（两层叠加）：①DPO 后的判官输出**多行美化 JSON**（带换行和
  长 reason），max_new_tokens=48 在闭合括号前截断；②评测解析器要求
  匹配完整 `{...}` 块——截断的半截 JSON 匹配失败 → None。54/60 题
  被误判为「未作答」，命中率指标把「解析失败」和「判错」混为一谈
- 决策：解析器降级为只抓 `"choice": "(甲|乙)"` 字母（本就只需要它）；
  max_new_tokens 放宽到 96；runner 改单样本逐条生成（批量左 padding
  路径与单样本结果不一致，DPO adapter 对 pad 更敏感）+ 逐题答案落盘
  可回溯
- 话术：「0.033 的命中率逼我做了三组对照实验，最后发现模型没崩，
  是我的评分器把『没说完』当成了『说错了』。评测器的解析失败和模型
  的判别失败混在同一个指标里，是评测基建最隐蔽的一种污染——这正
  是我们把解析率单独列为一等指标的原因」

### 62. 判官能力矩阵：0.5B 过得了偏好关，过不了阅读对齐关
- 现象：同一只 0.5B、同一套 DPO 配方、同量级训练对——偏好裁决判官
  命中率 0.93/0.87（η-a 达标），抽取忠实性判官 0.53/0.50/0.41
  ≈ 通用基线（η-b 未达标）。任务换了，能力不行了
- 根因：两个任务对模型的要求不在一个深度。偏好裁决（精炼 vs 求全）
  靠浅层特征（导语要素、篇幅、损伤痕迹）即可判；抽取忠实性要求
  「逐条事实回原文找依据」——真正的阅读对齐，0.5B 的能力下限之外
- 决策：把这条阴性变成产品能力——**判官能力矩阵**（任务 × 基座规模
  → 可用/不可用，全部由冻结 benchmark 便宜地测定）：0.5B 服役于
  偏好/质量裁决岗，忠实性判官需 1.5B+ 基座（租卡或量化）——任务
  分级 = 产品矩阵，这正是 benchmark 先行开发流程的业务产出
- 话术：「同一个 0.5B，两个任务，一个 0.93 一个 0.48——如果我没有
  先造 benchmark，我会把忠实性判官『训练成功』地上线，然后让一个
  随机数生成器给客户审数据。能力矩阵不是论文图表，是销售前的
  资质审核」

### 63. 泄漏检查在中文上的两层失真：模板前缀假阳性 + 字节 4-gram 塌缩
- 现象：θ 工坊给个人偏好 benchmark 跑泄漏检查，minhash 泄漏动辄几十条；
  回查 η-a 冻结的 pref_news_v1 manifest——**150/150 全量「泄漏」**，而文档
  是按对 holdout 结构性不相交的
- 根因（两层叠加）：①指纹打在整条 prompt 上——指令+协议模板头是所有题共享
  的常量前缀，MinHash 的极小值被共享前缀支配，band 签名大面积相同（真阳性
  率 100% 的假阳）；②`_minhash_keys` 用**字节级 4-gram**——UTF-8 中文首字节
  只有 E4~E9 约 6 种取值，跨字符边界的 gram 值空间极小，任意两段中文都有
  大量「天然共有 gram」，与模板无关也会撞 band（ASCII 实验对照：无关文本
  0/8 撞 band，同构中文合成语料 33/37）
- 决策：θ 通道指纹**投影到有效载荷**（_payload：截掉模板头 + 尾部输出指令）
  后再查，md5 泄漏作硬断言；minhash 在 CJK 上的灵敏度缺陷如实写进 manifest
  note——结构性隔离的硬保证是「按偏好对 holdout」的单测，不是带噪的指纹。
  字符级 gram 修复属 ζ 冻结资产语义变更，列候补池待立项，不在 θ 内顺手改
- 话术：「泄漏检查报 150/150 泄漏，第一反应不能是『改数据』或『改门限』，
  而是分层归因：先证明文档层不相交（结构性保证），再问指纹层在测什么——
  结果发现指纹打在了每道题都一样的模板上，等于给全班拍同一张证件照还说
  他们长得像。评测基建的假阳性和假阴性一样危险，因为它让人不再相信红灯」

### 64. 「最少标注量」是被考卷冻出来的一半：188 对学不动，488 对达标
- 现象：θ 工坊模拟用户 e2e，250 条标注（206 三元组）×2 epochs DPO——
  冻结考卷命中率 0.532，与通用基线 0.532 **完全持平**；训练账 rewards/acc

- 根因：DPO 的偏好判别是「逐步把 chosen/rejected 的 logp 差距拉开」的慢活，
  51 步（206×2ep/8）推不动，134 步（536×2ep/8）推开。判官没学会时指标
  不是「差一点」而是「恰好等于通用基线」——输出分布没被训练改变（对照题
  0.6 vs 0.33 的微弱差异来自损伤样本这种浅特征）
- 决策：把「最少标注量」当一等产品参数诚实呈现——向导建议量从 150 改

  强制留评测，追加标注全进训练）——否则每加一次数据就换一次考卷，
  学习曲线根本没法画
- 顺带修掉的坑：run_pref_benchmark 的 `--generic` 旧语义是「只跑通用」，
  带 adapters 时**静默跳过微调模型**——向导一次出双数字的用法会拿到底座
  分数还以为是自己判官的。语义改为「附加跑通用」，与 adapters 可同用
- 话术：「190 对点击训完，判官和没训过一模一样——最危险的失败不是变差，
  是没变化却长得像结果。冻结考卷 + 加量不换卷让『数据量-效果』曲线变成
  可复现实验：我们卖给用户的不只是判官，还有『你要点多少次才够』的诚实答案」

### 65. 真实数据一试跑就抓到「结果碰巧对、理由全错」：空白膨胀冒充低中文占比
- 现象：拿 2066 篇真实爬取新闻过文本漏斗，chinese_ratio 一级拦 778 篇
  （37.7%）；抽样审计发现被拦样本开头全是正常中文新闻（肉眼占比 0.77-0.90）
- 根因：爬虫抽取缺陷造成**空白膨胀**——被拦篇目空白占比中位数 77.2%
  （空格 3000+、\r 残留），「汉字/全文长度」被分母拖到 0.143 < 0.3 阈值。
  去空白后真实中文占比中位数 59.9%，**只有 5 篇是真非中文**；保留集空白
  中位数仅 1.4%——语料双峰（干净 vs 严重膨胀）。维基语料的下载器做过
  归一化，β 校准时从未暴露；**域迁移把「管线缺前置归一化算子」这个缺口
  照了出来**
- 决策：拦截结果碰巧接近对（膨胀页确实该清洗）但机制错误——正常比率
  略低的新闻会被同样误杀。修复方向已明确（爬虫端归一化 or 新增

**#68 全局统计算子的独立评测口径陷阱（V5 α）**
- 现象：工业漂移算子（sensor_drift，跨窗全局统计）在算子级独立评测中误杀 155 条
  干净窗（precision 50%），但漏斗串联门禁误杀只有 1.04%——同一算子同一语料，
  两个口径差 15 倍。「每个算子独立跑、丢弃互不影响」的评测口径对批量算子失效。
- 根因：独立评测把全量脏集（含 -999 计划外静默等灾难注入）喂给每个算子；
  静默窗的副本按 window_start 混进漂移基线，把基线中心/尺度拖垮，后续所有
  正常窗的 z 全部失真。单样本算子没有这个问题（逐条裁决互不影响）——「独立
  评测」的隐含前提是算子无状态，而全局统计算子天然有状态。
- 决策：①漂移基线中心/尺度改中位数（≤2/5 基线被污染仍稳健）——误杀 155→22、
  precision 50%→88%；②门禁以漏斗串联口径为准（上游质量算子先拦灾难窗，漂移
  在干净流上裁决——**算子顺序即架构**），报告中对独立评测口径加注；③教训入
  DOMAIN_PACKS 规范：批量算子的 P/R 解读必须带「与其他注入共存的口径」说明。
- 话术：「单样本算子的独立评测是干净的，因为逐条裁决互不影响；但漂移/去重
  这类全局统计算子，统计量本身就是全体样本的函数——把灾难注入混进来评测，
  相当于考官往考场里放噪音再怪考生发挥失常。工程答案有两层：统计上用中位数
  抗污染，架构上让质量算子先跑、漂移在干净流上裁决——顺序即架构」


**#69 不是算子缺一个，是协议缺一条（V6 α 改写通道）**
- 现象：想给漏斗补一层「文本归一化」（修 #65 现场：空白膨胀把中文占比分母撑爆、
  2066 篇误杀 778）。第一反应是写个新算子塞进 config——写不下去：算子协议是
  `score(sample) → 分数 + min/max 阈值`，全是**打分器**，没有一个能**改写样本**。
  #65 当时的修复记录原文就写着「盘点算子框架后确认所有算子都是打分器（score→阈值），

  实际是「协议缺一条通道」。**
- 根因：硬把它做成算子会出现病态——假设「改写算子」排在第 5 级，那前 4 级已经在
  **未改写**的文本上打完分了，后面的分级全部建立在脏输入上。改写的语义位置是

- 决策：新增与 `Operator` **并列**（非继承）的 `Transformer` 协议 + `TransformResult`

  默认空——**不改 Operator 签名、既有 config 一字不动**（V4「既有指标逐项相等」红线）。

  模态**——`fhir_resource` 的 `text` 承载 canonical JSON，`"given": ["John  Smith"]`
  里的双空格是数据不是噪声，与 C-MAPSS「恒定通道致 sensor_stuck 误杀 92.4%」同源。
- 话术：「这个坑最值钱的地方是它暴露了我的思维定式：**我发现'缺个东西'时的第一反应
  是去找插槽，而不是先问协议够不够表达这个语义。**归一化不是第 N 级滤芯，它是滤芯
  之前的一道工序——把它塞进算子序列，前几级就在脏文本上打分，整条链的语义就错了。

**#70 规则正交性：逐规则归因必须是纯的（V6 α）**
- 现象：归一化跑完，报告写「`whitespace_collapse` 命中 976 篇」。同一批单测里有三条
  却红了：`x\r\ny` 只开 `newline` 一条规则时也被改了、聚合里 `whitespace_collapse`
  的计数比预期少 1、子集规则的效果比预期大。三个红点指向同一件事。
- 根因：`whitespace_collapse` 收尾用了 `str.strip()`——它顺手吃掉了行尾的 `\r`。
  于是「命中 976 篇」里有一部分功劳其实属于换行归一化，而逐规则计数是给**阈值调优
  与归因分析**用的：归因不纯 = 每个数字都不可信，且没人能从数字上看出来。
- 决策：把规则职责切成互不重叠的七条——`newline` 独占 `\r`；`control_chars` **不删**
  `\r`（删了会把相邻行合并，那是改写不是清洗）；`whitespace_collapse` 的行内空白
  正则显式排除 `\r\n` 且只 `.strip(" ")`；`control_chars` 刻意留着 `\t` 好让空白
  折叠把它变**空格**而非直接删掉（`a\tb` 不该塌成 `ab`——替换与删除是两种语义）。
  实测修正后重跑：`whitespace_collapse` 976 / `newline` 891，两个数各自干净。
- 话术：「三条单测同时红，我一开始以为断言写紧了——其实是断言在替我发现一个
  **归因污染**：一个规则顺手干了另一个规则的活。逐规则统计一旦不纯，后面用它调的
  每一个阈值都是错的，而且错得看不出来。这类 bug 单测抓不到（功能上都对），
  靠的是'每个统计量必须只有一个来源'这条纪律。」

**#71 追加式台账 × 整文件聚合 = 报告无声漂移（V6 α）**
- 现象：改完报告渲染代码（把 markdown 表格行抽成构造器，纯格式化重构）后重跑，
  对照报告的数字变了——判据分布从 116/8128/20/49484 涨到 145/10160/25/61855。
  一个不影响语义的重构让报告变了，逻辑上不可能。
- 根因：判决书是**追加式 JSONL**（生产语义正确：一个台账存多次运行，靠 run_id 区分），
  而报告是**整文件聚合**的 `by_rule`。两者相撞：每重跑一次就往文件里加一整轮裁决，
  报告把历史运行一起统计。实测 57748 = 4 × 14437——**文件里已经躺着 4 轮**，
  准备这次重跑是第 5 轮。更糟的是 UI 侧同一个文件：阈值沙盘显示「这一级共 8264 个
  分数」，真实值是 2066，**整整 4 倍**。而 run_id 在两个口径里恒为 "A"/"B"，
  重跑不产生新 id，连过滤都做不到。
- 决策：①脚本侧「一次运行 = 一份干净台账」——重跑前**截断**（不是删目录：沙箱的
  批量删除护栏在本轮累计删除超阈值后会拦掉整个会话的删除操作，`write_text("")`
  是写不是删）；②加**不变量断言**：台账行数必须等于各滤级进入数之和，不等就
  `SystemExit` 把矛盾摔在脸上而不是让它漂移；③把行数写进报告正文。验收用
  「同码双跑逐字节相同」——可重跑本身成了缺陷的探针。
- 话术：「一个纯格式化重构让报告数字变了，这是最强的 bug 信号——**不可能**。
  顺着查是台账追加、报告整文件聚合，跑了 4 次就统计了 4 份。这类 bug 的可怕之处
  是它不报错、只漂移，而且漂得'像真的'：数字都是真实的裁决，只是重复了 4 遍。
  我的修法不只是删文件，是加了一条不变量断言，把'默默变大的计数'变成'立刻炸的
  异常'——**能漂移的指标必须配一条会炸的约束，否则它迟早变成一个无人察觉的谎。**」

**#72 清垃圾对象铲掉 22 个已推送的提交：把「ref 能读」当成「对象还在」（V6 α 收工）**
- 现象：清理一次误 `git add -A` 产生的垃圾对象时跑了 `git prune --expire now`。
  之后 `git rev-parse HEAD` 照常返回 `72c4fe3a`、`git status` 照常工作，**看起来一切
  正常**——但 `git cat-file -t HEAD` 直接 `fatal: could not get object info`，
  `git fsck` 报 **86 个 missing blob** + `refs/heads/main: invalid sha1 pointer`。
  reflog 里最近的 **22 个提交**（`1d894d6c` V3 η-b → `72c4fe3a` 证明链审计补强）
  在对象库里完全不存在：`count-objects -v` 从 `count: 394 / size: 85.58 MiB` 变成
  `count: 0 / size: 0`，而 3 个 pack 里只有旧的 55 提交 / 424 blob / 308 tree。
  **工作区文件一个没少**——丢的只有 `.git/objects`。
- 根因（两层，第二层才是真正的教训）：
  ①**这 22 个提交的对象当时只以「松散对象」形态存在**（γ/ε 之后没 repack），
  所以它们是彻底的裸文件，prune 删掉就是删掉，没有任何冗余副本。
  ②**`git rev-parse HEAD` 是一个假信号**：它只读 `.git/refs/heads/main` 那 41 字节的
  文件，**根本不碰对象库**。于是「HEAD 解析得出」和「这个提交在不在」是两件独立的
  事，前者会在后者已经烂掉之后继续正常返回——**最危险的故障是那个不报警的接口**。
- 决策/恢复：不接受「差不多能用」，要求对象级一致。环境事实：`github.com` 被沙箱
  代理挡（502 隧道失败），`codeload` 的 tarball 被限速到 ~22KB/s（9.2MB 要 418 秒）。
  **关键一步是别在真实仓库里直接 `git fetch`**——`refs/heads/main` 已指向丢失对象，
  协商阶段 git 会认为「我已有这个提交」从而什么都不下载（negotiation trap）。
  改为**在空的临时裸库里播种本地旧 pack + 把 ref 指到已知完好的祖先 `34907eec`**，
  服务器就只发增量：**20 秒 / 625KB / 312 个对象**（in-pack 787 → 1099）。
  验收（全部要求逐位一致，不接受近似）：`cat-file -t HEAD` 通过、
  `rev-list --count HEAD` = **77**（与远端一致）、`fsck --full --strict` **rc=0 零异常**、
  22/22 提交可读、`^{tree}` 解析 0 失败。
- 话术：「我用 `git prune --expire now` 清一个 85MB 的垃圾对象目录，代价是铲掉了
  22 个已经推到远端的提交。但真正值得讲的是**我为什么没发现**——因为
  `git rev-parse HEAD` 一直正常返回。它只读那个 41 字节的 ref 文件，不碰对象库：
  **ref 解析成功和对象存在，是两件独立的事**，真正的健康检查是
  `git cat-file -t HEAD` 或 `git fsck`。恢复时的第一个错是直接在真实仓库
  `git fetch`——主分支 ref 已指向丢失的提交，协商会说『我有了』然后什么都不下载；
  正确做法是拿一个已知完好的祖先当协商锚点，只拉增量，20 秒完事。
  收成两条纪律：**①对象是唯一不可再生的资产，动 `objects/` 之前先
  `git bundle create` 或 `cp -r .git`（工作区丢了能重写，对象丢了要靠网络）；
  ②用『超时』当『失败』的证据之前先量一次吞吐**——我把 codeload 的限速误判成
  『卡死』三次，实际第一块就要等 46 秒。」

### 66. 抽取层对照：兜底器 60/60 成功但绝不能当默认——以及站专用抽取器的两个真实缺陷
- 现象（W2-6，**60 篇真实页面**，同一份原始 HTML 三档各抽一次；`data/reports/extract_ablation.{json,md}`）：
  - `news_cn`（tier0 站点专用）**49/60**（11 篇 `抽不出`）
  - `heuristic`（tier2 stdlib 兜底）**60/60**
  - `trafilatura`（tier1 通用库）**未安装** → 60 条 `unavailable`，**从分母剔除**
  - 交叉：**救回率 100%（11/11）、丢失率 0%**
  - **但**：同页字数比 p50 **1.92×**、**多抽段占比 88.9%**、基准段被覆盖 89.5%
- 根因（逐条抽查归因，不是笼统结论）：
  1. **站点抽取器会删掉段落内部的行内链接文本**。它拿 `<a\s[^>]*>.*?</a>` + DOTALL 在
     **整个容器段**上做替换，于是
     `<p>　　<a target='_blank' href='/'>中新社</a>上海9月20日电 …</p>`
     变成 `上海9月20日电 …`——**导语开头的机构署名整批消失**。
     而这条路径**正是产出既有 2066 篇语料的那条路径**。
  2. **跨段的 `<a>` 会把多段内容拼成一段**：实测「未被覆盖」的基准段在**原始 HTML 里
     都不是连续子串**（长度 460 / 519 的两条明显是两段正文被并成一段），
     说明删除动作跨过了 `</p><p>` 边界。段落边界本身就是下游特征
     （段数、噪声段占比、按段规则都在用它），所以这不是「少几个字」。
  3. **兜底器把侧栏推荐位整批抽进正文**：多出的段落绝大多数是「白宫高官减脂餐」
     「干眼不只是眼睛缺水」这类热门推荐标题，每页 40+ 条。这解释了 1.92× 的字数比，
     也再次说明 **`n_chars` 更大 ≠ 抽得更好**。
- 一个必须记住的**指标陷阱**（我自己先踩了）：
  - 做段落包含判断前**必须 `html.unescape` 归一**。兜底器会把 `Fijo&#322;ek` 还原成
    `Fijołek`，而站点档刻意不还原（要保持历史落库文本逐字不变）。不归一时同一个词
    被判成「字面不同」，**覆盖率被系统性低估**：实测把 **11.15%** 的基准段错判成
    「未被覆盖」，归一后是 **10.49%**。
  - 教训：**报任何「覆盖率/漏抽率」比值之前，先确认两侧的文本归一化口径一致**，
    否则量到的是口径差异，不是内容差异。
- 决策：
  - 兜底器的定位写死为 **「保证从不失败」，而不是「更好的抽取器」**；它留在 tier2
    （只在前面都失败时才启用）是对的。
  - **站点档那两个缺陷暂不修**：修它会改变既有 2066 篇语料的落库文本，等于换语料，
    必须配独立 A/B，不能顺手改（与本项目「既有数字逐项相等」的红线一致）。已记待办。
  - W2-6 的**人工抽检 30 篇只产出对照表**（`data/reports/extract_review_sample.jsonl`，
    `human_verdict` 留空待填）。报告里明确写「不含人工质量判定」——
    **不拿代理指标冒充人工结论**。
- 话术：「三档抽取器跑在 60 篇真实页面上，结果不是『谁赢』，而是三件不同的事：
  站点档 49/60 成功、兜底器 60/60 且能把 11 篇失败页全部救回、通用库没装所以不计分
  ——注意我没把『没装』算成『跑输』。但兜底器救回全部失败页的代价是字数 1.92 倍、
  88.9% 的段落是多出来的，我抽查后发现多出来的是侧栏推荐位标题。所以它的价值是
  『保证流水线不断』而不是『抽得更好』，设成默认会把 40 条无关标题写进正文、
  污染下游所有算子。顺带还查出站点档一个真缺陷：它的 `<a>` 剥离正则会删掉段落
  **内部**的行内链接文本，导语里的『中新社』署名整批消失，而这条路径正是我既有
  2066 篇语料用的路径——这个发现比对照结论更值钱，因为它说明我的语料在进漏斗之前
  就已经缺字了。」

### 67. 同一个事实，两个算子给相反的答案是**对的**：设备级停机 vs 单通道卡死
- 现象（P2 修复 R1/R3，MetroPT-3 真实数据 41478 窗）：把 7 个通道的时刻对齐后，
  发现 **191 个窗 × 7 通道 = 1337 条**记录是**全通道同步冻结**（聚成 7 段连续块，
  最短 5.1 小时、最长 61.4 小时）。这 1337 条在旧 `sensor_stuck` 下**全部**判为
  「卡死」→ 计入误杀；而官方故障标签里它们是 **0/191**，检修记录里也是 **0/191**。
- 根因：`sensor_stuck` 的判据形态（窗内极差为 0）在真实数据里有**两种含义**——
  ①某个通道的传感器坏了（该判「不可用」）②整台设备停机（该判「这窗不适用」）。
  旧判据只看单通道，把②也吃成了①。**形态相同、含义相反。**
- 结论（裁决方式是关键）：判据里加一条**设备级豁免**，唯一的判据是
  **跨通道同步性**（同一 `(device_id, window_start)` 下 ≥2 个通道同时恒定）——
  不看时长、不看是否在检修记录里（检修记录只覆盖到的部分，拿它当依据会漏）。
  然后**两个算子对同一批窗给不同答案，而这是对的**：
  - `sensor_stuck` → `score=None`：「我这项判据在这窗上**不适用**」
  - `fault_vs_maintenance` → `1.0` + 证据 `machine_stop`：「这不是故障，是停机」
  两条路径共用**同一个** `_device_stop_keys()`（单一真相源），所以不会各算各的。
- 数字：MetroPT-3 上 `sensor_stuck` 误杀 **4.36% → 1.07%**，同时 300 次真脏命中一条不丢；
  `fault_vs_maintenance` 从「恒过」（真实数据里根本没有 `-999` 哨兵形态，判据空转）
  变成 707 窗如实记 `None`。
- 话术：「真实数据给我上的第一课是：**同一个观测形态可以有两种含义**。我的传感器卡死
  判据在 1337 条记录上判『卡死』，但把 7 个通道的时间戳对齐一看，是**整台设备那段时间
  停机**——191 个窗、7 个通道一起冻结，最长的连续 61 小时。官方故障标签在这 191 个窗上
  一个都没标，检修记录也没记。我没有去猜一个时长阈值，而是用**跨通道同步性**当唯一判据：
  两个以上通道同时冻结才算设备停机。然后有意思的地方来了——修完之后，我的两个算子对
  同一批窗给出了**相反**的判决：卡死算子说『不适用』，故障判别算子说『这是停机不是故障』。
  这两个答案都对，因为它们回答的是不同的问题。这件事我专门写了测试锁住，因为『两个算子
  打架』在 code review 时最容易被当成 bug 顺手改错。」

### 68. 「注入即复制」让一整类判据在合成轨上**结构性不可达**
- 现象（P2 修复 R5）：给 `sensor_stuck` 新加的「持续尺度塌陷」档（需**连续 ≥10 窗**
  尺度塌陷）写端到端验收时，**合成轨上一窗都抓不到**。我第一反应是判据写错了。
- 根因（写诊断脚本量出来的）：合成污染器的注入方式是**「复制供体窗 → 保留原窗 →
  两份都放回」**，两个副本的 `window_start` **相同**；而算子内部按
  `(window_start, id)` **全序**排序——于是副本被插在原窗**后面**，
  游程每两窗就重置一次。实测 12 个通道的最长连续游程只有 **3~5**，门槛是 10。
  **不是判据错，是合成轨的注入几何表达不了「连续 N 窗」这件事。**
- 结论：拆成两条测试，各锁一件事——
  1. `min_run=1`（摘掉连续性这一个维度）验**形态归属**：命中率 ≥0.9，且只由
     `scale_collapse` 命中、干净集零误杀 → 证明「噪声平坦线」这个形态被新档认出来了；
  2. 把「注入即复制 → 最长游程 3~5 < 门槛 10」**钉成断言**，作为防回归：
     哪天有人改了污染器的注入几何，这条会红，提醒他重新评估端到端验收。
- 通用教训：**合成轨的注入器只表达「它会的那些形态」**。给判据加一个「跨窗/上下文」
  维度（连续 N 窗、滑动窗口、时序因果）时，默认假设「合成能造出靶子」是错的，
  要先把**靶子可达性**量出来——**「抓不到」和「没靶子」是两件完全不同的事**。

### 69. 参考尺度取「健康窗 σ 的 p75」有一个 75% 的硬上界（已知边界，钉成断言）
- 现象：`sensor_stuck` 的塌陷档要跟一个「正常尺度」比，参考尺度取**健康窗（窗内极差≠0）
  的 σ 的 p75**。写测试时用「3 个健康窗 + 12 个塌陷窗」跑，**塌陷一个都没抓到**；
  改成「10 健康 + 12 塌陷」立刻正常。
- 根因：健康窗占比 20%（= 塌陷占比 80% > 75%）时，**p75 落进了塌陷窗的 σ 区间**，
  参考尺度被塌陷样本自己拉低 → 门槛跟着掉 → 塌陷档整体失效。
  这不是 bug，是「用分位数当参考尺度」的固有性质：分位数一旦越过「坏样本占比」，
  它就变成了坏样本的分位数。
- 结论：不改成更复杂的鲁棒估计（那会把架构拖重），而是**把边界如实写下来并钉成测试**
  `test_stuck_reference_scale_collapses_when_most_windows_are_collapsed`，
  同时在函数 docstring 里写明「塌陷窗占比 > 75% 时本档失效」。
- 话术：「我的卡死判据要拿一个『正常波动有多大』当尺子，我取的是健康窗标准差的 75 分位。
  写测试的时候撞到一个边界：如果我造的塌陷窗超过四分之三，75 分位就落进**塌陷窗自己**
  的波动里了——尺子被要量的东西拉低，整档失效。我没有为了这个边界去堆一个更复杂的
  鲁棒估计，而是算清楚这个数、写进 docstring、**并且钉成一条会红的测试**。
  面试里我更想讲的是这个判断：**知道一个边界在哪、并且让它有名有姓，比掩盖它更有价值**。」

### 70. 两处「口径自相矛盾」：品牌数字串档 + 声明与数据编码打架
- 现象一（串档）：演示门户里图文页写着「**11 级滤芯**」，而同页总览的实点数
  `OP_COUNT = 29`。按「先实点再改」的纪律去查注册表：模态是
  `image_caption / text_article / fhir_resource / industrial_sensor` 四值，
  **图文实点是 12 个**（8 纯图文 + 4 图文/文本双模态），而 **11 恰好是 `text_article`
  的数量**——两个数字串了档。**照抄「29」去改同样是错的**（29 是跨模态总数）。
- 现象二（假精确）：我自己写的预计算 JSON 里有一个 `state_code` 字段声明
  `{"0":"未评","1":"通过","2":"丢弃"}`，而实际 `d`/`d0` 数组**只有 0/1 两个取值**
  （通过/丢弃），「未评」根本不在里面（它是另一个字段 `u` = 未评算子数）。
  更糟的是**没有任何消费者读它**——它只是躺在那儿等着下一个人照着写错。
- 结论：
  1. 品牌数字改成**从注册表现算**（`_modality_counts()`），取不到就退回定性说法
     （「多级滤芯」）——**宁可不说数字，也不编数字**；并加一条测试把
     「blurb 里的数字 == 注册表实点」绑死，以后加算子会自己跟上、串档会立刻红。
  2. `state_code` 直接**删掉**，换成如实描述各数组编码的 `columns` 字段。
- 通用教训：**「口径打架」往往不是笔误，而是「手写 + 无消费者校验」的必然结果**。
  修法不是把两个数字对齐，而是**把数字接到唯一真相源上**；
  以及——**没有任何消费者的字段，是负资产**：它唯一的作用是误导后来人。

### 71. 真实轨召回低（21.9%）的第一根因是**标签语义错配**，不是判据不灵
- 实点（现场重跑 `scripts/eval_real_sensor.py --source cmapss`）：29757 窗
  （干净 25557 / 脏 4200）→ 保留 28031（94.2%）；并集去重后
  **真实脏命中 919/4200 = 召回 21.9%**，**真实干净误杀 807/25557 = 3.16%**。
- 先把三个数据集的真实标签摊开看语义（`labels["dirty"]`）：
  | 数据集 | 标签 | 条数 | 它到底是什么 |
  |---|---|---|---|
  | C-MAPSS | `degraded` | 4200 | 发动机**运行到失效的物理退化** |
  | MetroPT-3 | `fault_window_air_leak` | 819 | **空气泄漏过程故障** |
  | SKAB | `sensor_anomaly` | 512 | **过程异常**（水泵阀件试验台） |
- **三个数据集没有一个提供「数据质量缺陷」的真值。** 而五个工业算子判的是
  卡死 / 越界 / 偏移 / 单位混用 / 链路静默——**数据质量维度**的缺陷。
  拿「设备坏了」当「数据脏」的分母，召回天然只有两成，而且**这不是算子不够好，
  是分母错了**：退化的传感器读数本身完全合法（机器坏了，传感器没坏）。
- 逐条拆开 C-MAPSS 的 4200 条脏窗（读算子自己写的 `evidence.rule`，不外部猜）：
  `sensor_stuck` 抓到 **124（3.0%）**，全是 `exact_flat`；
  未评 **1212（28.9%）**（落在全寿命恒定的 6 个通道上，无信息通道豁免）；
  **评了但过 2864（68.2%）**。`sensor_range` 100% 未评；
  `unit_consistency` / `fault_vs_maintenance` 100% 评了但过（这两份数据没有它们的靶子）。
  所以「漏掉的 78%」里绝大多数**读数上没有任何数据质量缺陷**。
- 话术：「我的真实轨召回 21.9%，我没有把它当成绩。查下去发现分母是错的——
  C-MAPSS 的标签是『发动机退化』、MetroPT-3 是『空气泄漏』，都是**过程/设备异常**；
  我的算子判的是**数据质量缺陷**。这两件事在工业界是明确分开的两条线，
  我把它们混在一个召回分母里，等于拿数据质量检测器去考故障诊断。
  **修正口径比调阈值重要**——调阈值只会让误杀上去换一个假的好看。」

### 72. 判据的分组长度假设在真实数据上不成立：`_BASELINE=5` 遇上「每组只有 6 个窗」
- 实点（C-MAPSS）：`device_id` 是 **200 台发动机**（`cmapss_fd001_unit001`…），
  21 个通道，`(device_id, channel, operating_mode)` 共 4200 组，
  **每组窗数 min/中位/max = 4 / 6 / 17**。
- `sensor_drift` 的 `_BASELINE = 5` 意味着：**中位数情况下只有 1 个窗能被判决**
  （前 5 个窗估中心与尺度，剩下的窗才是判决对象）。而尺度 `pooled` 还是
  「5 个窗的窗内 σ 取中位 × AR(1) 有限样本因子」外推来的——
  **5 个样本估一个 σ，再拿它当 4σ 门槛的尺子**。
- 这不是调参能救的：`_BASELINE` 显然是为「一通道几百窗」的长序列设计的
  （合成轨常态），到了「一台设备一条命只有 6 段」的切片上，
  **基线长度必须随可用窗数自适应**，否则判据在结构上就没法工作。
- 通用教训：**判据里每一个"常数"都是一个未声明的数据形状假设**。
  `_BASELINE=5`、`min_run=10`、`α`、`z=4` 都是。真实数据一换形状，
  先别问阈值合不合适，先问**这个常数还成不成立**。
- 顺带：C-MAPSS 没有真实时间戳，`window_start` 是 ingest 时造的相对占位时间轴
  （`2000-01-01T00:00:00` + 30 小时步长，共 17 个取值）。它**单调、可排序**，
  所以「按时间排序取前 5 个窗当基线」逻辑上成立——但**它排的是相对顺序，
  不是真实工况时间**，讲的时候不能含糊成「按真实时间取的基线」。

### 73. 单变量统计量在 C-MAPSS 上 AUC 只有 0.63：缺的是**维度**，不是判据形态
- 我原本的假设是「判据只做电平偏移、没有趋势项，所以抓不到缓慢退化」。**实测推翻了它。**
- 对照实验（同一批窗、同一 σ̂、同一分组，只换统计量，
  用 Mann-Whitney 秩和算 AUC，0.5 = 与随机猜无异）：

  | 统计量 | AUC |
  |---|---|
  | 现判据：`|窗均值 − 基线中位数| / σ̂`（电平偏移） | **0.6272** |
  | 假设缺的：`|窗均值的局部 OLS 斜率| / σ̂`（K=10） | **0.6333** |
  | 两者取大（= 把趋势项并进判据） | **0.6254** |

  三个都是 **0.63 上下 ≈ 几乎不可分**。加趋势项**一点没改善**（0.6272 → 0.6333，
  且在「两者取大」时还降了）。
- 结论：**不是判据形态缺一项，是单变量层面根本没有足够信息**。
  C-MAPSS 的退化是 21 个通道**我们一起动**的联合现象；任何「一通道一个阈值」
  的判据族（不管阈值多好、加多少种单变量统计量）都只能拿到 AUC≈0.63 的上限。
- 行业正解就是把维度显式建出来：**MSPC（多变量统计过程控制）**，
  标准做法是 PCA 后看两个统计量——
  **Hotelling's T²**（「在模型能解释的方向上偏离了多远」）与
  **SPE / Q 残差**（「出现了模型没见过的模式」）。
  文献里对 SPE 的描述几乎就是在描述我们的场景：
  「**即使单变量都在历史范围内，缓慢漂移的传感器也会让 SPE 升高**」。
- 通用教训：**先把「信号在不在」量出来，再决定改判据还是改维度**。
  AUC 这个动作很便宜（不训练、不调参），但它能把「调参调不动」从玄学变成结论：
  **AUC≈0.5 的时候，任何阈值工程都是浪费**。我用一次 AUC 否掉了自己一个
  看起来很合理的假设，这比省下的时间值钱。
- 话术：「我一开始以为是判据少了趋势项。量了 AUC：电平 0.627、趋势 0.633、
  两者取大 0.625——三个都是『几乎不可分』。**加趋势项没用**。
  这告诉我信息不在单变量里，21 个通道是联合变化的，
  该上 MSPC 的 T²/SPE，而不是继续调阈值。**我用一个不训练、不调参的
  AUC 对照，把自己一个很合理的假设否掉了。**」

### 74. 一个判据从「零触发」到「全量饱和」只差一个字（all vs ≥2），
### 以及归因必须读算子自己的证据
- 现象：`_device_stop_keys` 的门槛是「同一 `(device_id, window_start)` 下
  **全部**通道的读数都恒定」（`all(...)`），且至少 2 个通道。
  在 C-MAPSS 上实测：**1417 个键里满足「全通道恒定」的是 0 个** →
  停机豁免**一次都没触发**（这是对的，C-MAPSS 不产停机）。
  但**100% 的键都满足「≥2 个通道恒定」**（因为 s1/s5/s10/s16/s18/s19
  这 6 个通道**全程恒定**，每个键上都躺着这 6 个恒定的）。
- 也就是说：**如果当初门槛写成 `≥2`，这个判据会 100% 饱和**，
  把 29757 个窗**全部豁免成 `None`**——一个看起来更"宽松更安全"的写法，
  实际把整个算子变成空转。
- 附带的一个方法论教训（我当场踩了）：我先写了个归因探针，
  **用自己重新算的「≥2 通道恒定」去解释未评来源**，结论是
  「8406 条未评全部来自停机豁免」。**这是错的**——停机豁免在 C-MAPSS 上触发 0 次；
  真正的 8406 条来自「无信息通道豁免」（6 个全寿命恒定通道）。
  我之所以发现错了，是因为「100% 的键都满足判据」这个数字**太干净、不可信**，
  于是去读了算子自己写进 `meta["evidence:<op>"]` 的 `rule`，而不是继续猜。
- 通用教训：
  1. **判据里的 `all` / `any` / `≥N` 是一个会决定生死的设计决定**，
     必须用真实数据量一遍「这条件在这份数据上触发了百分之多少」。
     **触发率 0% 和 100% 都是坏味道**（不误触发是运气，全量触发是空转）。
  2. **归因要读被测系统自己记录的理由，不要在外面重算一个近似判据去解释它。**
     重算的判据和真判据只要差一个字，结论就完全反了。
     而且——**"太干净的数字"本身是一个信号**，值得多问一句。

### 75. 教科书写法「参考集 99 分位」在小参考集上会退化成**静默空转**
- 现象：给 MSPC 层（`sensor_multivariate`）写控制限时，按教科书惯例取
  「参考集上的 99 分位 × margin」。向真实窗注入 **330 条已知缺陷**，
  该算子召回 **0.0%** —— 一条都没抓到，且**不报任何错**。
- 根因：`n=50` 时 99 分位**就是最大值**，再乘 margin 之后没有任何点能超过它。
  参考集越小越严重，而工控场景的参考集（每台设备寿命最早的 30% 窗）恰恰很小。
  这类错误的可怕之处在于：**它表现为「判据通过了所有数据」，而不是报错。**
- 决策：换成**稳健限** `中位数 + margin × 1.4826×MAD`
  （`src/mm_curation/operators/robust.py`）。同一批注入的召回从 0% 变成有意义的量级。
  并把这条教训写进函数 docstring —— 下一个读代码的人会先看到「**刻意不用** 99 分位」
  和它为什么，而不是"这里怎么没按教科书写"。
- 通用教训：
  1. **分位数是有「样本量前提」的统计量**，小样本下它会静默退化到极值。
     凡是「取某个高分位当阈值」的写法，都要问一句 `n` 多小的时候它会等于 max。
  2. **判据要能证明自己「在工作」**，不能只在被触发时才有信号。
     这就是后来 R10 覆盖率闸门的动机（见 #76）。

### 76. 「未评」和「零召回」在报告里长得**一模一样**
- 现象：`sensor_range`（量程检查）在三个真实数据集上，报告的召回那列永远是
  `0.0%`。看上去像「它判过、这份数据很干净」，实际上它**一次都没评过** ——
  真实数据集的 `(device_type, channel)` 基本都落在内嵌手册量程表外，
  协议规定表外记 `None`（无法计分），于是它什么都没做。
- 更早的一版更糟：表外通道记 `1.0`，报告读起来像「量程**全部通过**」，
  实际也是**一次都没评**——两种错法都指向同一件事：
  **报告只印了「丢了多少」，没印「评了多少」。**
- 决策（R10，2026-09-22）：
  1. 评测报告给每个算子同时印**已评覆盖率**与召回，覆盖率 <50% 或为 0 时
     该行标 `ALL_UNSCORED` / `LOW_COVERAGE` + `<<< 召回不可引用`，
     并在结论里写明「**不是零召回，是没有分母**」；
  2. 覆盖率口径限定在**读数窗**上（那是被判的对象，非窗记录不是清洗的分母）；
  3. `explain` 把两种未评分原因分开（`no_range_entry` 要去找手册量程，
     `insufficient_reference` 要等更多参考数据）——对使用者是两件事。
- 顺带修掉一处**真实的**分母口径错误：背景自带异常率的**分子含「被注入替换掉的
  原窗」**，而分母不含 → 系统性虚高。修正后三个数据集的漏斗背景率各降约 0.4pp
  （C-MAPSS 6.17%→5.74%、MetroPT-3 6.48%→6.05%、SKAB 4.46%→4.06%）。
  这是「两侧必须同分母」这条纪律的又一个实例。
- 通用教训：**一个「什么都没做」的判据，在只印结果不印分母的报告里，
  和「做得很好的判据」是不可区分的。** 报告必须自带「这次到底评了多少」。

### 77. 用数据自己的分布定边界，在遇到**工况漂移**时会把一半真实数据判成越界
- 背景：为修 #76，给 `sensor_range` 补了第二条边界来源 —— **数据包络**
  （`scripts/build_envelopes.py`：取每组最早的 30% 窗作参考段，
  按 `中位数 ± margin×1.4826×MAD` 定读数级边界，跨设备取并集）。
  这在 C-MAPSS / SKAB 上效果很好：召回从 0% 涨到 35.1% / 43.5%，
  且包络自身的「背景自带异常率」只有 1.16% / 0.66%。
- 现象：同样的配方在 **MetroPT-3** 上，包络的背景自带异常率是 **54.40%**
  （漏斗级 56.29%）—— **一半以上的真实数据被判成越界**。
  这在本项目的纪律里是不可接受的（真实轨对外只能讲「低误杀」）。
- 根因：固定参考段隐含了「数据稳态」这个**未声明的假设**。
  MetroPT-3 是真实压缩机数据，工况（负载/启停）在持续变化，
  参考期的工作点套到后面的工况上当然大面积越界。
  C-MAPSS 是仿真退化数据（工况平稳）、SKAB 是小试验台（工况恒定），
  所以前两个数据集**掩盖**了这个问题 —— 这也是「一个默认值吃遍所有数据集」
  这种做法的典型失败方式。
- 决策：给**生成端**加**留出集自检** —— 边界仍只由参考段**拟合**，
  但用参考段**之外**的读数做接受/拒绝检验（这是留出集验证，不是
  「用整份数据调边界」，不构成同义反复）：留出集越界率 > 5% 的组，
  **整条边界不写入**，宁可让判据记未评。实测效果：
  MetroPT-3 的包络背景异常率 **54.40% → 0.43%**，同时漏斗注入召回
  **81.2% → 89.9%**（因为不再被误判淹没）；C-MAPSS / SKAB 的召回不受损。
- 通用教训：
  1. **「从数据里学一个边界」必须先声明稳态假设**，并用**留出集**验证它成立；
     否则模型在平稳数据上表现良好，只是因为你还没遇到会漂移的那份数据。
  2. **负样本数据集的选型是评测设计的一部分**：如果三个数据集都工况平稳，
     你会得出「这个方法很稳」的错误结论。MetroPT-3 在这里的价值就在于**它拆台**。
  3. 生成端与判据端对「不可靠的输入」要有同一个态度：**宁可未评，不给坏值**
     （与 #76、`sensor_drift` 的 `mad` 档同一纪律）。
