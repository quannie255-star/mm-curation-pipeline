# PRD：双项目日常运维系统（ops-flywheel）—— 30 天数据飞轮

> 状态：✅ 用户已确认开工（2026-09-15）。一期（R0-R4）设计表已落 design_tables.md
> OPS w1 节，代码已入库（scripts/ops_daily.py + fetch_finance_news.py +
> ops_install_schedule.py + configs/text_funnel_finance.yaml）。宿主仓库决策：
> mm-curation 内开发（用户确认），抽离触发条件见开发日志。勘误两条：股票池对齐
> findata UNIVERSE 实际口径 25 只（本文写作 50）；findata 已自带 daily_pipeline
> （含告警推送通道），R1 推送在 findata 侧免费获得。
> 本文件是 30 天日常运维的需求单一事实源。
> 服务对象：findata（仓库级巡检）+ mm-curation-pipeline（采样级清洗/判官）两个在役项目。

## 一、定位（一句话）

> 把两个"手动复现的作品集仓库"变成"每天自己转的在役系统"：连续 30 天、每天定时
> 采集 A 股数据（结构化行情 + 个股新闻文本）→ 双管道加工 → 一份日报 → 每周从真实
> 暴露的问题里挑 2-3 个回填优化；第 4 周在飞轮之上长出最简策略骨架 + 模拟盘。

## 二、为什么需要运维系统（三个理由）

1. **"维护数据管道"的面试主张需要在役证据**。JD 关键词的完整含义是"写 + 养"；
   现在两个仓库只有"写"的证据（ETL 代码、数据 CI），没有"养"的证据（连续在役、
   告警-归因-修复的完整记录）。30 天运维日志就是这份证据。
2. **真实数据优化闭环需要日常化**。chinese_ratio 事件（129 测试全绿、真实数据
   一跑就抓出 773 篇误杀）证明真实数据轮是全项目最有价值的质量动作，但它至今
   是一次性事件。做精 = 制度化。
3. **交易雏形需要一个每天产出的底座**。策略、判官、回测都是飞轮上的消费者；
   没有日常数据底座，第 4 周的策略骨架没有输入。

## 三、设计原则

**每条需求对应一个"没有它必然发生的具体事故"**（现象→事故→需求，与工程笔记
同构）。凡列不出事故的需求，进 Out 或候补池。

## 四、需求清单（R0-R9）

### R0 调度层：每日定时触发
- **事故**：第 5 天忘跑/出差/睡过头 → 数据断档，且无法区分"忘了跑"和"上游挂了"。
- **需求**：每日 20:00 定时触发单入口命令（收盘数据已稳定、当日新闻基本齐）；
  至少一次触发语义；错过补跑不产生重复数据（幂等由 findata ingest 保证，调度层
  只管触发）。
- **实现约束**：Windows 任务计划程序优先（Airflow docker 已有但维护成本高，
  30 天验证期不为了优雅加复杂度）；任务计划设"错过后尽快补跑"。

### R1 采集健康与断采告警
- **事故**：akshare 接口改版（30 天内大概率 1-2 次），管道静默产出 0 行——
  只有"跑完了"没有"跑出了多少"，坏 10 天才发现。
- **需求**：每次采集记录行数与失败清单（findata `tracked_run` 已有，直接读）；
  当日行数低于预期带（如前 7 天中位数的 50%）→ 告警；告警复用 findata 的
  `UPSTREAM_STALE` / `UPSTREAM_MISSING` 归因语义。
- **为什么**：坏了自己知道而不是事后知道——这是"维护管道"与"跑管道"的分水岭。

### R2 文本采集适配器（唯一新写的采集代码）
- **事故**：没有文本接入，mm-curation 半边没数据（findata 只有结构化表）。
- **需求**：akshare 个股新闻 → Sample JSONL（`id` / `text` / `meta{source,
  symbol, fetch_run_id, crawled_at}`）；每 symbol 每日 top N（默认 20）条定量；
  robots 合规/限速/幂等纪律沿用 ζ1 爬虫；50 只股票池起步（复用 findata UNIVERSE）。
- **为什么带血缘字段**：下游漏斗丢弃审计要能回溯到"哪天、哪个源、哪只股票"，
  否则 R5 的审计没有上游可归因。

### R3 每日管道编排（单入口，非零即停）
- **事故**：手工按顺序跑 6 个命令，某天顺序错/漏跑一步，产物不一致且无感知。
- **需求**：单入口（建议 `python scripts/ops_daily.py`）按固定顺序执行：
  ① 结构化采集（findata `ingest_all`）→ ② 文本采集（R2）→ ③ DQ 巡检
  （findata 探针+归因）→ ④ 文本漏斗（mm-curation 金融漏斗 config）→
  ⑤ 丢弃审计（R5）→ ⑥ 日报（R4）。任一步退出码非零即停止并进日报"今日异常"。
- **为什么非零即停要显式做**：η-b 期间的教训——管道吞错 exit 0 不可信（DEV_PLAN
  2026-09-05 在案），编排层必须自己校验每步产物存在且非空。

### R4 每日复盘报告（人只看这一份）
- **事故**：数据散在多个 report json 里，第 10 天就没人看了；人的注意力是
  最先耗尽的资源。
- **需求**：`data/reports/daily/YYYY-MM-DD.md`，结构固定：
  顶部三行"今日异常"（无异常则写"无"）→ 采集行数（结构化/文本，与 7 日均值
  对比）→ DQ 告警与抑制 → 漏斗保留率 → 丢弃模式 top3 → （第 4 周起）策略信号
  与模拟盘动作 → 磁盘水位。中文输出 `-X utf8`。
- **为什么 Markdown 不做 Web**：沿用仓库 Out 清单传统（不做真前端）；
  日报 + 文件查看器对单人运维足够。

### R5 丢弃审计入口（真实数据轮的固定化）
- **事故**：审计 `dropped.jsonl` 靠想起来才做 → 优化永动机空转。
- **需求**：`ops_daily.py --audit-only` 或日报内嵌：按 `dropped_by` 聚合当日
  丢弃 + 每类随机抽 3 条人工可读样例 + 疑似误杀标记（对照保留集分布）。
- **为什么**：chinese_ratio 事件的产出全靠人工审计挖出来；制度化后每天 5 分钟。

### R6 优化清单（时间盒纪律的载体）
- **事故**：真实数据每天暴露一堆想改的东西，随手全改 → 飞轮停转（30 天计划
  最大超载风险）。
- **需求**：单一 backlog 文件（建议 `docs/ops_backlog.md`，格式沿用 DEV_PLAN
  候补池）：**每日只记不改**；每周复盘挑 2-3 个做；完成回写来源运营日期——
  每个优化可溯源到"第几天暴露"。
- **为什么算运维系统的一部分**：30 天验收里"项目被真实数据优化 ≥3 个 bug"
  没有载体就没有验收。

### R7 数据与磁盘生命周期
- **事故**：30 天 × 全量 JSONL + 索引 + 报告，磁盘写满后管道静默失败。
- **需求**：磁盘水位检查进日报（>80% 标红）；原始新闻按周压缩归档；
  数据不入库口径不变（日报可重生成，周报关键数字按协议回写 DEV_PLAN）。

### R8 环境冻结（开工前一次性还债）
- **事故**：`.venv` 已坏、系统 Python/akshare 升级破坏 API → 全链路断，
  且 30 天中段修环境最伤节奏。
- **需求**：开工日一次性做三件事：① uv 一键可复现环境（锁文件真实生效，
  README 快速开始收敛为两条命令）；② 冻结依赖版本（运维 30 天内不升级）；
  ③ 机器电源设置常开 + 关闭自动更新重启。
- **为什么放运维 PRD**：这 30 天的"维护"本质是在冻定的环境上跑，环境漂移是
  最大的单点风险；这也是作品集"clone 30 分钟跑通"承诺的前置债。

### R9 周报（趋势与决策节奏）
- **事故**：只有日报 → 单日波动掩盖趋势，优化挑选与策略观察没有依据。
- **需求**：每周日自动汇总：在役可用率、告警次数与归因分布、保留率趋势、
  优化清单消化情况、（第 4 周起）模拟盘周报。关键数字按协议回写 DEV_PLAN
  开发日志。

## 五、Out（明确不做，防蔓延）

- **实盘下单**：个人自动交易无合规通道（券商接口违反 ToS；QMT/Ptrade 有资金
  门槛）——模拟盘代替。这是红线不是裁剪。
- Web 界面 / 移动端推送（日报文件 + 控制台足够）。
- 多机 / 云 / 分布式（单机 30 天验证）。
- 分钟级/高频数据（日线 + 新闻足够雏形）。
- 策略迭代与调参（第 4 周只搭骨架，回测必须带手续费并注明 30 天无统计意义）。
- 告警接钉钉/邮件（第一版 = 日报置顶标红，前提是你每天真的看）。

## 六、架构（薄壳原则：ops 只编排不实现）

```
Windows 任务计划程序（每日 20:00，错过后补跑）
   └─> python scripts/ops_daily.py            ← 唯一新写的编排壳
        1. ingest_structured   复用 findata ingest_all（幂等增量+血缘）
        2. ingest_text         新写：akshare 新闻 → Sample JSONL（R2）
        3. dq_monitor          复用 findata 探针+归因；断采告警（R1）
        4. funnel              复用 mm-curation 漏斗（金融 config）
        5. audit               dropped_by 聚合 + 抽样（R5）
        6. report              日报 + 磁盘水位（R4/R7）
每周日：python scripts/ops_weekly.py         ← 周报 + 优化挑选（R6/R9）
```

依赖方向：ops 调两个项目的既有入口命令，不 import 内部实现；两项目接口变更
在 ops 壳一处适配。

## 七、验收标准（30 天）

1. **在役**：无人值守成功 ≥25/30 天；每次断采由告警/日报发现而非人发现（次数入周报）。
2. **产物**：日报 30 份、周报 4 份，格式完整率 100%。
3. **优化**：真实数据暴露并修复的算子/管道 bug ≥3 个，每个可溯源到暴露日期。
4. **环境**：新环境 `uv sync` + 两条命令全链路可复现。
5. **判官**（第 3 周）：judge_finance_v1 冻结 benchmark + κ 出数。
6. **策略**（第 4 周）：带手续费回测报告 + 模拟盘接通 + 每日信号进日报；
   报告注明统计局限。

## 九、约束与风险

| 项 | 现实 | 对策 |
|---|---|---|
| akshare 接口改版 | 30 天内大概率 1-2 次 | 重试 + 降级（缩股票池）+ 归因告警；每次坏接口本身是在役素材 |
| Windows 休眠/自动更新 | 个人机常态 | R8 电源设置；任务计划"错过补跑" |
| 磁盘写满 | 静默失败最难缠 | R7 水位进日报 |
| 自己不看日报 | 人的注意力耗尽 | R4 顶部"今日异常"三行；违者日报无意义化 |
| 超载（顺手改个不停） | 30 天计划最大风险 | R6 每日只记、每周挑 2-3 |
| 单机故障 | 30 天中段最伤 | 数据可重生成口径 + 周报关键数字回写 DEV_PLAN（留痕不丢） |
