# PRD：个人微调平台（personal-tuner）—— 首战「专属数据判官」

> 状态：已确认开工（2026-09-03，用户确认锚点与算力路线）。
> 本 PRD 是 V3 阶段的单一事实源，变更须回写本文件。
> 与现有项目的关系：**叠加不重写**——V2 的数据管道/评测协议/CI 是本平台的地基。

## 一、产品定位（一句话）

> 让个人研究者用「**自己的数据 → 自己的 benchmark → 自己的模型**」三步完成领域微调，
> 全程数字可验证——把市面上需要复杂工作流的模型训练，变成一条个人可驾驭的流水线。

差异化：LLaMA-Factory/Unsloth 把「微调」做成了商品（训练层我们薄封装不自研）；
通用 benchmark 评不了「我 care 的能力」（评测集构建无人在做）；
**个人化的 benchmark 构建 + 数据工程闭环是本产品的自研核心**。

## 二、锚点问题（首战）：专属数据判官

**问题**：数据管道的 L3 质量裁决层，「规则抓不干净、通用大模型判不准且贵」。
δ 阶段实证：通用 Qwen2.5-0.5B 在中文网页语料上做质量判官，κ(t) 全阈值域 ≈0
（判分与脏净零相关）——**通用模型不认识你的数据域**。

**解法**：用本平台四步造出该域的专属判官——
1. **获取**：接原始数据源（公开数据集 / 可爬源 / 个人文档导入）进统一 Sample 协议
2. **清洗**：现有 V2 漏斗直接复用（规则/去重/困惑度）
3. **造训练对**：程序化污染（已验证的方法论）→ 带质量标注的 (文本, 分数) 对
4. **微调+评测**：Qwen2.5-0.5B LoRA → 在**冻结的域 benchmark** 上结算 κ——
   目标：κ 从通用的 ~0 提升到 **≥0.5**，并报告域外泛化（诚实呈现）

**为什么它是真实业务问题**：每个数据团队都有这一层——规则维护成本高、
LLM 打分 API 按条收费。专属小判官 = 一次微调成本换无限次廉价高质量打分。

**平台化叙事**：首战跑通后，「换一个数据域 = 换一份配置」——判官只是第一个
示范任务，同一套「数据→benchmark→微调→评测」骨架可套任何个人微调需求
（风格模仿、领域问答、信息抽取）。

## 三、用户故事

- 个人研究者：把我爬的 5 万篇文档变成干净训练集，并且**知道**它有多干净
- 数据工程师：规则维护不动了，用自己域的数据微调一个 0.5B 判官替换 30 条正则
- 求职作品集读者：clone 仓库 → 跑 RUNBOOK → 30 分钟看到「κ 从 0 到 0.5+」的完整证据链

## 四、范围

**In（首战必做）**
- 数据获取器：≥1 个新原始源（网页爬取）+ 统一进 Sample 协议；robots 合规、限速、幂等
- benchmark 构建器：从域语料构建**版本冻结**的评测集（防污染：与训练集去重；
  准入：构建过程的一致性指标；可复现：seed 固定）→ `benchmarks/<name>.jsonl` + manifest
- LoRA 微调器：peft + Qwen2.5-0.5B（本机 8GB）；YAML 训练配置；实验 ledger 落盘
- 评测 runner：训前/训后自动跑 benchmark → 对比报告（κ、P/R、解析率）
- 端到端案例：维基/新闻域判官，数字进 README

**Out（明确不做，防蔓延）**
- 训练框架自研/多 GPU/基模预训练（方法论对齐，不是规模对齐）
- Web UI（Streamlit 加一个 tab 展示结果即可）
- 通用 benchmark 接入（C-Eval 等）、模型仓库/注册中心、多用户
- vLLM 部署（Windows 不可用；推理用 transformers 直出足够 0.5B）

## 五、架构（四层）

```
┌────────────────────────────────────────────────────────┐
│ A 应用层   fetch(数据获取) → funnel(V2复用) →            │
│            benchmark(冻结评测集) → tune(LoRA) → report   │
├────────────────────────────────────────────────────────┤
│ B 自研层   benchmark 构建器（防污染/准入/版本化）★核心    │
│            评测 runner（κ/P/R/解析率，δ 已有零件）        │
│            数据获取器（爬虫/导入器，Sample 协议统一）      │
├────────────────────────────────────────────────────────┤
│ C 薄封装   peft + transformers LoRA（YAML 配置驱动；      │
│            实验 ledger：配置+loss+评测数字追加式落盘）    │
├────────────────────────────────────────────────────────┤
│ D 地基(V2) Sample 协议 · 漏斗执行器(local/ray) · 去重 ·   │
│            污染器 · kappa · 数据 CI · 权重入口            │
└────────────────────────────────────────────────────────┘
依赖方向永远向下；D 层不改（除非有明确协议缺口）。
```

## 六、验收标准（模块级）

1. **获取**：新源爬取 ≥2000 篇正文进 `data/raw/<source>_corpus.jsonl`（幂等重跑不重复）
2. **benchmark**：冻结评测集 ≥300 条，manifest 含版本/seed/来源指纹；
   与训练集 md5+minhash 双重去重（防泄漏）；泄漏检查有测试
3. **微调**：LoRA 在本机 8GB 跑通（loss 曲线 + 配置落盘）；实验 ledger 可追溯
4. **效果**：冻结 benchmark 上 κ ≥ 0.5（对照：通用模型 κ≈0.013）；
   P/R、解析率、延迟全部进报告；**域外数据上的泛化数字如实呈现**
5. **工程**：全链路测试绿（FakeClient/离线 mock，CI 零 GPU）；RUNBOOK 一键复现

## 八、约束与风险

| 项 | 现实 | 对策 |
|---|---|---|
| 算力 | 本机 RTX 4060 8GB + Windows | 0.5B LoRA 本机；7B 级后续租卡（AutoDL ~¥2/h）；Unsloth/vLLM 不支持 Windows → 全用 transformers+peft 栈 |
| 爬虫脆弱 | 站点改版即失效 | 解析与站点结构解耦（配置化选择器）；单源挂了换源不阻塞平台叙事 |
| benchmark 主观性 | 「质量」定义因人而异 | 正是产品点：benchmark 版本化 + 标注协议进 manifest；kappa 量化和基准的分歧 |
| 合成判官数据偏 | 污染器造的脏 ≠ 真实脏 | benchmark 含真实脏样本分层；泛化数字如实报告（已在验收 4） |
