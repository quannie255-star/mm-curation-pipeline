# 差距分析：本项目 vs 业界 SOTA

> **定位**：本文不是「许愿清单」。每条差距都标注①代码里的**实证依据**（读到了什么）、
> ②业界 SOTA 的**出处**、③**不补会怎样**（代价，可证伪）、④**补的成本**。
> 判据层级纪律见 [ENGINEERING_NOTES.md](ENGINEERING_NOTES.md)；
> 本文所有本项目数字的唯一真相源是 [claims.json](claims.json) + `data/reports/*.json`。
>
> 日期：2026-10-08。SOTA 水位以 DataComp-LM（240T token 池、53 个下游任务）
> 与 DataComp（12.8B 图文对、38–53 任务）为准。

---

## 零、先说结论

项目**不是**「做得差」，而是**判据层级选错了赛道**。

已具备的工程能力（协议抽象、双运行时、四模态、判决书、台账、门禁）
在 JD 口径上已经很强——比DataComp 那种「拼算力拼数据量」的路线更适合工程岗。
但**对外证明「我的数据更好」这件事，业界已经不用 P:R 了**。

DataComp-LM 的实证结论（直接引用）：

1. **SOTA 判据 = 下游模型涨多少**（53 个下游任务 MMLU/Core），不是检出率。
2. **人类标注不可靠地预测训练效用**：16 位标注者、499 篇、71% 一致率下，
   AskLLM 约 82% ROC-AUC 最贴人类标签，但下游模型**显著差于**几个只有约 73% ROC-AUC
   的 fastText 过滤器。→ **「我的过滤器 P:R 高」不是「我的数据好」的证据。**
3. **模型式质量过滤是主导干预**，且**廉价 bigram 分类器胜过昂贵的 LLM 打分**
   （1B 档fastText 30.2 Core > Perplexity 29.0 > AskLLM 28.6 > Semantic dedup 27.1）。
   且结论是「**正例分布定义得好，比分类器 sophistication 更重要**」。
4. **去重的具体实现次要**：Bloom filter 与 MinHash+suffix array 几乎同分（MMLU 44.3 vs 44.4），
   都比不去重好 2.1 Core；但**去重超参会改变分布**——5-token 最小 n-gram 保留 Core
   却重创 MMLU。→ 「把去重做对」的天花板不高，但「配错」会伤下游。
5. **混入传统「高质量」源可能反噬**：DCLM-BASeline 加 RedPajama −1.2 Core。
   → 「多源混合=更好」是错的，混比是独立决策面。
6. **人类判断不可靠→ 不能用「人觉得干净」当训练集正例**。
   本项目 `wm_nsfw_cnn` 用合成水印做训练集（A/B 风格组防记住），
   方向与第6 条一致；但**正例分布是否匹配下游任务分布从未验过**。

## 一、G1（最致命）：缺「训练效用」判据层

### 实证依据
- 现有全部质量证据是 **P:R / 检出率 / 误杀率**：
  `scripts/eval_detection_slo.py`、`eval_operators.py`、`operator_pr.json`。
- 训练级验证只有两处，且**都跑在合成污染上**：
  `scripts/finetune_gpt2.py`（GPT-2 zh，脏语料 vs 干净语料 ppl）
  与 `scripts/finetune_clip.py`（Chinese-CLIP 干净/脏集微调 → 检索指标）。
- 真实干净数据上已实测过一次（`scripts/eval_real_coco_evidence.py`）：
  净贡献 R@1 **+0.0107**（0.546→0.558），而**丢弃 35 条里只有 7 条（20%）
  是硬事实**（文本逐字节相同），`semantic_dedup` 14 条仅 1 条 → 丢弃量2.16%
  是真实冗余 0.37% 的 5.6 倍 = **过度清洗**。
  → 也就是说：在真实数据上，本项目的净收益只有 **1pp 量级**。
- `docs/claims.json` 里 `soul_dirty_r1` / `soul_clean_r1` 是**检索 R@1**，
  属代理指标，不是训练效用。

### 不补会怎样
**这是「对外说数据更好」唯一的致命缺口。**
按 DataComp-LM 第 2 条，一个P:R 90% 的过滤器完全可能对下游模型毫无帮助甚至有害。
本项目现在**无法回答**「清洗后训练出的模型比不清洗好吗」——这正是面试官
按 JD「数据策略」追问的第一个问题，也是把项目从「清洗工具」升格为
「数据工程体系」的分水岭。

### 补的成本
**低-中**。已有两块地基：`finetune_gpt2.py` 的等步数对照协议、
`eval_retrieval.py` 的固定评测集。缺的是把两者接成一条流水线，
并在**真实干净数据**上跑（不是合成污染）。

## 二、G2：去重缺「精确子串」层

### 实证依据
`src/mm_curation/operators/dedup.py` 只有三件套：
`md5_exact`（字节级）、`phash_near`（感知哈希，海明阈值 12，**O(n²)**）、
`minhash_lsh`（字符 3-gram，Jaccard 0.65）。

全仓 grep `suffix` / `bloom` → **零命中**（只有 `.suffix` 文件后缀的误匹配）。

### 与 SOTA 的差距
DataComp-LM 对比过三种去重：**exact + MinHash + suffix array** 与
**Bloom filter**（7B-2x 档几乎同分）。本项目三件套里，
`md5_exact`≈exact、`minhash_lsh`≈MinHash，**缺 suffix array 那一层**。

suffix array 抓的是 MinHash 会漏的那一类：**共享大段逐字连续子串**
（模板 boilerplate、许可证头、爬虫注入片段）。这正是本项目
`boilerplate` 算子在**单文档内**做的事——但没有跨文档。

⚠️ 注意 DataComp-LM 的限定：**「5-token 最小 n-gram 保留 Core 但重创 MMLU」**。
所以这一层的阈值不能拍脑袋，必须做小规模对照。

### 不补会怎样
`boilerplate_inject` 形态的召回天花板只有 **23.3%**（30 条挤在 7 段互异描述里，
其余被 minhash_lsh 当重复处理）——**这个「天花板」有一部分是装置造成的，
不是算子能力上限**。补上子串层能直接抬高这一格的实测上限。

### 补的成本
**中**。suffix array 本身是经典算法（`datasketch` 无此实现，需自己写或用
`pydivsufsort`/`suffixarray`）。难点不在实现，在**阈值的对照实验**。

## 三、G3：过滤器是「无监督阈值」，SOTA 是「学到的分类器」

### 实证依据
15 个算子里，判据型算子（`text_length` / `chinese_ratio` / `char_repetition` /
`line_repetition` / `boilerplate` / `pii_detect` / `clip_alignment`）全部是
**手调阈值**。阈值来源是 ROADMAP 记的「实测分离度间隙中点」——
例如 boilerplate 0.90、pii 0.83、line_repetition 0.67。

**这不是偷懒，是有意为之**：阈值取自实测间隙而非拍脑袋，且有 `threshold_scan.py`
与 `threshold_regression_gate.py` 在守护。问题在于**方法论层面**：
无监督阈值回答的是「这条脏不脏」，SOTA 的模型分类器回答的是
「这个样本对下游任务有没有用」。

DataComp-LM 第 1 条：模型式过滤是主导干预，且 **cheap bigram classifier 胜过 LLM 打分**；
第 3 条里更关键的一句是「**定义正例参考分布，比分类器 sophistication 更重要**」。

### 本项目其实有一半
`detector/model.py`（MobileNetV3-Small 三分类 clean/watermark/ad_nsfw）
已经是图像侧的「学到的分类器」，且 `detector/synth.py` 用了 **A/B 风格组**
（布局/透明度/字体/文本池四维错开）防循环论证——**这个设计恰好呼应
DataComp-LM 第 6 条**（人觉得干净≠对下游有用，所以正例分布必须显式设计）。

缺的是**文本侧**的同等物，以及「正例分布是否匹配下游任务」的验证。

### 不补会怎样
在JD 面试里会被问：「你的阈值对不同领域怎么迁移？」
当前答案（靠实测间隙 + 回归门禁）能守住工程质量，但**说不到「数据策略」层面**。

### 补的成本
**中**。文本侧分类器（如 fastText bigram）实现不复杂，
但需要一条「正例分布定义 → 训练 → 跨域验证」的流水线。

## 四、G4：数据混比（mixing）是空白面

### 实证依据
`sampling/sampler.py` 有 Random / Stratified / SemanticPrune 三个采样器，
但**它们都是在「已清洗池」内选子集**，不是「多源如何配比」。
`data/connectors.py` 597 行是多源连接器，`docs/DOMAIN_PACKS.md` 有领域包，
但**没有任何一处定义「源 A 与源 B 混多少」**。

### 与 SOTA 的差距
DataComp-LM 第 5 条是**反直觉且直接相关**的：
「混入传统高质量源可能反噬」——C4+2.2、RedPajama+1.7、RefinedWeb+1.4，
但**DCLM-BASELINE −1.2**。即「已充分过滤的语料加传统高质量源会让模型变差」。
第 3 条也提醒：Wikipedia/books/arXiv/GitHub 单独加进去都**没能**提升 DCLM 语料。

→ 含义：**混比是一个需要实验决定的决策面，不是「多源=更好」的常识**。
本项目目前根本没有这个决策面。

### 不补会怎样
如果对外讲「多源接入」，DataComp 的证据说明这**本身不是优势**。
项目现在的真实优势是**单源深挖 + 可信门禁**——这更该讲透，而不是扩源。

### 补的成本
**中**（但依赖 G1：没有训练效用判据，混比实验没有裁决标准）。

## 五、规模层：O(n²) 与非分布式去重

### 实证依据
- `phash_near`：`next((k for k, kh in kept if h - kh <= threshold), None)`
  —— **对已保留集线性扫描**，整体 O(n²)，且 `shardable=False`。
- `minhash_lsh` / `md5_exact`：`shardable=False`（全局索引）。
- 已有 Ray 运行时（`RayDistributedExecutor`）但只对 `shardable=True` 的算子有效。
- 分区裁剪已有字节级证据（2736 B / 1885232 B → 少扫 99.85%）。

### 与 SOTA 的差距
DataComp 的 12.8B 对规模用 Rust 实现的去重 + Bloom filter（选它正是为了可扩展性）。
本项目 `phash_near` 在万级样本上就不可用。

**这一条我认为不该补**（见下节优先级）：万级规模下 O(n²) 完全够用，
而补分布式去重会把项目拖回「拼规模」的赛道，违背「一条线」的收敛决策。

不接 CI = 这份承诺只在开发者本机成立。这是**叙事与事实的直接冲突**。

### 补的成本
**低**（workflow 文件 + 一次实跑）。这是**性价比最高的一条**。

## 八、需要人拍板的三个架构决策

下面三项**会改变项目定位或叙事主线**，不属于实现细节，必须先定：

### 决策 A：G1 的实验口径——「训练效用」用什么模型测？

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A1 复用现有 GPT-2 zh 微调 | 干净集 vs 清洗后集，等步数比 held-out ppl | 地基已有，改动最小 | ppl 对「脏」敏感度低（首轮差仅 0.4%） |
| A2 复用现有 Chinese-CLIP | 干净 vs 清洗后，等步数微调比 R@1 | 已有两套 `.pt` 权重 | 图像侧，文字脏数据无直接对应 |
| A3 两臂都做，取一致结论 | 文本看 ppl，图文看 R@1 | 结论不易被单指标绑架 | 工作量 ≈ A1+A2 |
| A4 引入 DataComp 式固定训练集 | 小模型 + 固定 recipe + 多任务评测 | 最接近 SOTA 口径 | 远超当前规模，需新算力 |

**我的建议：A3**。理由：单指标容易翻车（记忆里已有「指标出现极端组合时先怀疑判据」
的教训），两臂一致才算证据。

### 决策 B：要不要把「合成污染」从「主证据」降为「装置自检」？

现状：绝大多数召回数字来自合成污染注入（ROADMAP 自己标注
「94.8% 是合成污染下的数字，与真实轨口径不同、不许混」）。
但真实轨实测净收益只有 +1pp、且 80% 丢弃需人工确认。

| 选项 | 说明 |
|---|---|
| B1 保持现状 | 合成轨当主证据，真实轨当补充 |
| **B2 降级**（建议） | 合成轨只证明「装置能自检」，主证据换成真实轨逐条可归因的低误杀 |
| B3 双轨并列 | 两条各占一半篇幅 |

B2 的代价是**叙事会变弱**（真实轨 +1pp 不如 94.8% 好看），
但收益是**对外不被追问即破**：只要有人问「合成污染算不算循环论证」，
B1 就守不住。

### 决策 C：G2 的阈值怎么定？

suffix array 的「共享子串多长算重复」没有普适值——
DataComp-LM 明确说 5-token n-gram 能保 Core 但重伤 MMLU。

| 选项 | 说明 |
|---|---|
| C1 固定阈值（如 50token） | 简单，但无证据支撑 |
| **C2 小规模对照后设**（建议） | 在现有黄金集上做 3–5 档对照，选「误杀不涨」的最高档 |
| C3 按源分别设阈值 | 最贴合业务，但需要每源都有评测集 |

## 八点五、本轮实施结果（2026-10-08，决策 A3+B2，四项全做）

| 差距项 | 状态 | 实测结果 | 产物 |
|---|---|---|---|
| **G6门禁接 CI** | ✅ 完成 | 4 个工作流全部可解析；`verify_claims` + 5 个变异测试接CI；模拟干净检出预演通过 | `.github/workflows/gate-ci.yml` |
| **G2 suffix array 去重** | ✅ 完成 | 算法层 36 条测试全绿（SA vs 朴素 60 组随机串全一致、LCP 全一致）；5 个跨篇场景全过 + 归因正确 | `src/mm_curation/operators/substring_dedup.py` |
| **G3 文本质量分类器** | ⚠️ 完成但**天花板如实记录** | A 组 balance 0.927；held-out B 组 0.546，泛化 gap −0.381，门禁**主动判 FAIL** | `src/mm_curation/text_quality_classifier.py` + `data/reports/text_quality_classifier.md` |
| **G1 训练效用** | 🔄 进行中 | 三臂等量对照 + 噪声地板（见下） | `scripts/eval_training_utility.py` |

### G6 顺带修掉的一个**假绿缺陷**

`verify_claims.py` 原来把 `missing` / `pointer-broken` 只打进汇总行、**不计入红项**，
`return 1 if n_drift else 0` 因此在 CI（干净检出、无 `data/reports/`）上返回 0
—— **16 条 claim 的锁定在 CI 上完全失效且报告为绿**。
已加 `--reports-missing {fail,skip}`，默认 `fail`（红），CI 显式用 `skip` 并打印豁免数。

同时把 `no_yaml_comment_collision.py` 的扫描范围从 `configs/` 扩到
`.github/workflows/`（14 → 18 个 YAML），并补上**冒号粘连**这一形态判据
（我当场就在新工作流里犯了 `- name:断言`，只查「`#` 粘连」抓不到）。
两个形态都做过双向验证：正确实现不误红、错误实现必变红、还原后回绿。

### G3 的三条可复用实测结论

1. `TfidfVectorizer(analyzer="char_wb")` 学到的是**具体字符**，不是**形态**
   —— 同一形态（尾部重复堆叠）换字面量：`-` → 1.000，`（详情）` → 0.070。
2. 泛化只能靠**显式结构特征**补：加与字面量无关的档位 token 后，
   未见过的零宽字符召回 0.020 → **0.930**。
3. **判据必须与数据形态匹配**：3-gram 重复率在本项目短文本语料上恒真
   （干净 0.137~0.451 vs 损伤 0.259，完全重叠）→ 必须换成最长游程 + 行级唯一度。

### G4 的前提变了（如实记录）

原计划「源 A 与源 B 混多少」在动手前实测发现：
`data/raw/text_corpus.jsonl` 的 30.2 万条**全部来自单一源 `wikipedia-zh`**，
「源混比」在这份语料上**不成立**。可用的真实异质文本源只有三个：

| 语料 | 条数 | 文本长度中位 | source |
|---|---|---|---|
| `text_corpus.jsonl` | 302002 | 158 | `wikipedia-zh` |
| `news_corpus.jsonl` | 2066 | 1422 | `chinanews` |
| `finance_news/news_corpus.jsonl` | **214** | 160 | 25 个财经媒体 |

形态差异极大（长度中位 158 vs 1422），且财经源只有 214 条。
**混比实验需要先定口径**（等量？对长度分桶？）与**数据量是否补足**，
属需人拍板范围，见下节决策 D。

## 八点六、G1 与 G4 的实跑结论

### G1 训练效用：**清洗在本批文本上显著更差**（超出噪声地板 4.46 倍）

三臂等量对照（各 4711 条，等步数 600，同 held-out 800）+ 噪声地板：

| 臂 | held-out ppl |
|---|---|
| base（不微调） | 15.7219 |
| unclean_matched（不过漏斗） | 7.8637 |
| cleaned（过漏斗） | 8.0587 |
| noise_probe（同数据不同 seed） | 7.8200 |

- Δ（unclean − cleaned）= **−0.1950**（相对 −2.48%）
- 噪声地板 = |probe − ref| = **0.0437**
- |Δ| / 噪声地板 = **4.46 倍** → 判定：**cleaned 显著更差（值得查漏斗是否过度清洗）**

⚠️ **本条结论 2026-10-09 翻转过一次，原结论是错的。** 原判据写的是
`noise_floor = results["noise_probe"]`，即噪声臂的**绝对 ppl（7.82）**，
而 Δ 是**差值（0.195）**——拿绝对量当差值的门槛，`|Δ| < 7.82` **永远成立**，
于是「测不出差异」这个看起来很谨慎的结论，其实是一个**恒真的免责条款**：
报告照常生成、措辞体面，但换任何实验它都给不出结论。
隐蔽之处在于**日志里算的是对的**（`abs(probe − ref)` = 0.0437），只有判据取错了量。

修法三条：① `compute_noise_floor()` 独立成函数，量纲由测试锁住
② md 标题改为**由 verdict 现算**（此前手写的标题与 JSON 口径分叉，
人读的那份说「测不出」、机读的那份说「显著更差」）
③ `tests/test_training_utility_criterion.py`（7 条）双向验证过两个变异：
噪声地板退回绝对值、判定方向写反，**全被拦红**。

**与真实 COCO 实测同向且互相印证**：那边净贡献 R@1 只有 **+1pp**，
且丢弃的 35 条里只有 **7 条（20%）是硬事实** —— 「丢弃量是真实冗余的 5.6 倍」
与「文本侧清洗让模型更差」是同一件事的两种测量。
**过度清洗**这条判断现在有两条独立证据。

**第一版的错误必须留档**：不加等量对照时，`unclean` 臂用全量 6000、
`cleaned`臂 4711，等步数下后者数据池更小 → 报出 Δ = **−0.1101**（「清洗更差」）。
那是**口径错**（质量与数量混成一个变量），不是清洗的错。
修法：`--equal-size` 默认开；`--unequal-size` 只回答「值不值得为质量牺牲 X% 数据量」。

>⚠️ **边界不变**：这是**代理的训练效用**（小模型 + 固定 held-out ppl），
> **不是** DataComp-LM 口径（固定 recipe + 53 个下游任务）。
> 且只测了**文本侧** —— 图文侧的 CLIP 微调（clean_ft 0.688 vs dirty_ft 0.636）
> 走的是另一条口径，两者**不许混**。

## G4 数据混比：结论与其边界（实跑，2026-10-08）

每臂 200 条 · 500 步 · seed 42 · held-out 150 · 本地 `gpt2-chinese-cluecorpussmall` · CUDA。
完整报告 `data/reports/source_mixing.md`（由 payload 现算，不手工维护）。

**可归因的四个臂**（长度中位 149–171、丢弃率 9–11%，wiki 占比是唯一变量）：

| 区间 | Δppl | 倍噪声地板 | 判定 |
|---|---|---|---|
| 100% → 80% wiki | +0.0040 | 0.89× | **测不出** |
| 80% → 50% wiki | +1.1343 | 254× | 显著变差 |
| 50% → 33% wiki | +3.1051 | 695× | 显著变差 |

**结论**：本三源组合下，**混入量在 20% 以内测不出差异；超过 20% 后ppl 显著单调上升**。
与 DataComp「混高质量源可能反噬」方向一致，但那是跨规模结论，本实验只是这一组三源。

**两个臂不可归因**，其ppl 不能用来论证「该源质量差」：
- `mono_news`（45.19）：长度中位 653，是其余臂的 4 倍 → 混着长度效应。
- `mono_finance`（31.27）：过漏斗丢弃 **22.5%**（其余臂 9–11%）→ 混着选择性丢弃。

**可复现性**：同批数据重跑（换 seed 做噪声探针）得 `mono_wiki` 1.5046 vs 1.5002，
差 0.0045 = 噪声地板；上一轮独立跑批得 1.5062/1.5129，量级一致。

**如实未做 / 数据边界**：
- `finance` 源仅 **214** 条 → 全局上限被压到 214 条/臂，
  样本量偏小，**结论只能是方向性的**。
- `mono_news` 长度中位 653，而混比臂 164~171 →
  **长度变量没完全对齐**（混比臂被 wiki 拉低）。
  即便如此仍跑完，但报数时必须带上这个混淆。
- 未做「不混入长度变量」的严格版（需按长度分桶后配比，样本量进一步下降）。

## 九、明确不补的（写下来比装看不见强）

- **分布式/大规模去重**：万级规模下 O(n²) 不是瓶颈，补它违背「一条线」收敛决策。
- **音视频新模态**：ROADMAP 已明确不追。
- **PB/EB 级实跑**：算力约束，且与岗位无关。
- **Agent 行为数据 / RLHF 全链路**：会引入全新数据来源，与主线正交。
