## 零、先说这一篇的立场

用户原话：**「项目最重要的目的不是炫技而是推销，证明我能干一个什么什么样的活。」**

所以本篇不按「技术亮点」组织，按**岗位产物**组织。每个补充项都要通过一道过滤：

> **JD 可写性测试**：补完它，我能不能在简历上写出一句「我做过 X（业务动作）」？
> - ❌ 「我加了 DuckDB 层」——这是技术，不是活
> - ✅ 「我用 SQL 建了指标口径层，口径变更由 CI 校验」——这是活

过不了这道测试的功能，一律不做。

## 一、调研：两条赛道的真实岗位产物

### 1.1 DS/DA 线（含实习）—— 8 份真实 JD 的共性

把 5 份在招数据分析实习 JD + 1 份行业实习指南拆成「岗位实际交付什么」：

| 岗位产物 | JD 原话（摘） | 本项目现状 |
|---|---|---|
| **取数 SQL**（多表 JOIN / 窗口函数 / CTE） | 「熟练掌握 SQL（**硬性要求**）」「能独立编写复杂 SQL」 | ❌ **无 SQL 层** |
| **指标口径统一** | 「参与 KPI 体系梳理与制定，**统一数据口径**，确保业务方对指标理解的一致性」「指标口径确认」 | 🟡 口径纪律极强（`claims.json` + `verify_claims.py`），但**没有「指标字典」这个产物形态** |
| **业务指标看板** | 「协助搭建和维护业务核心指标数据看板」「看数模板」 | 🟡 有 Streamlit 八页签 + 运维日报，但**不是业务指标看板** |
| **AB 实验设计与评估** | 「实验方案设计、指标体系搭建、分流配置与实验监控」「效果评估、归因分析、**显著性检验**」 | ✅ **强**：随机删 baseline 因果对照、剂量-响应、分层采样对照（`random_drop_baseline.json`、`ablation_eval.json`） |
| **专题分析报告** | 「输出分析报告」「结论沉淀」「专项数据报告的撰写与呈现」 | 🟡 有工程报告，**缺 DS 口味的分析报告**（问题→结论→建议） |
| **数据监控与异常预警** | 「实时跟踪核心业务线进展，**及时发现并预警异常数据波动**」 | ✅ PSI 漂移监控 + 数据 CI 门禁 |
| **数据对账 / 异常排查** | 「能独立完成**数据对账、异常排查**」「定位数据差异原因」 | 🟡 审计飞轮抓到真实线上 46 条域误杀，但**未产品化** |
| **数据字典 / 文档** | 「Data dictionary or project README」「Data quality checks: QA checklist or anomaly report」 | 🟡 README 有，**数据字典无** |

**一条值得注意的 JD 原话**：「**口径错误可能导致业务决策失误，必须严谨**」（众安保险实习 JD）。

> 这句话是本项目在这个赛道上的**最大卖点入口**——项目的全部纪律都长在「口径」上，
> 只是现在没有用 DS 岗听得懂的形态表达出来。

| 岗位产物 | 本项目现状 |

### 1.4 开源竞品：这个领域已经分成三条线

调研结论（`shipshapedata` 2026 年综述）：**数据可观测性工具分三类，成熟团队用两到三类组合，而不是找一个大而全的平台。**

| 线 | 代表项目 | 干什么 |
|---|---|---|
| **质量测试** | Great Expectations（11.8k★）/ Soda Core / Deequ / DQOps / Elementary | 断言驱动：人手写 expectation，跑校验 |
| **目录与血缘** | DataHub（12.6k★）/ OpenMetadata / **OpenLineage + Marquez** / ODD | 元数据、血缘、资产目录、影响分析 |
| **基础设施监控** | OpenTelemetry / Prometheus / Grafana | 管道健康、延迟、失败 |

**两个可直接借鉴的产物形态**：

1. **Great Expectations 的 `Data Docs`**——把校验结果**自动渲染成给人看的文档**，
   还有「用大白话表达测试结果」这一条明确产品目标。→ 对应我们的**质量记分卡**。
2. **OpenMetadata 的 data health score**——把 profiling + 质量测试套件汇总成
   **单资产健康度**，配 owner 与任务流。→ 同样对应质量记分卡。

**本项目与它们的真实差异（必须讲清楚，否则显得在重复造轮子）**：

- GX / Soda 是**断言驱动**：规则是人写的，工具只回答「这条断言过了没有」。
- 本项目是**污染器驱动的 P/R 闭环**：能回答「**这条规则本身灵不灵、召回多少、误杀多少、
  在真实数据上有没有适用性**」。

> 这个差异是真的，但**必须翻译成岗位语言**：
> 「我能为每条数据质量规则给出召回率与误杀率，并标注它在真实数据上是否适用
> （而不是只有『通过 / 不通过』）。」
> 而**不是**「我有个污染器」（面试官不知道那是什么，也不关心）。

## 二、判断：缺的不是能力，是**产物形态**

把上面三张表合起来看，结论很清楚：

**本项目在「质量规则的严格程度」上远超岗位要求，在「岗位产物的标准形态」上几乎全缺。**

具体是三类缺口：

| 缺口类型 | 表现 | 为什么致命 |
|---|---|---|
| **入口缺口** | 无 SQL 层 | DA / 数据开发岗的**唯一硬门槛**，其他再强也过不了技能关 |
| **形态缺口** | 有口径纪律但无指标字典；有质量数字但无记分卡 / SLO；有血缘原料但无图无契约 | 面试官看不到他能认出的东西 → **看不懂等于没有** |
| **叙事缺口** | 报告是工程口吻（「R1–R6 修复」「等价性三口径」），不是 DS 口吻（「问题 → 结论 → 建议」） | 岗位考的是「你能不能把数据讲成结论」，不是「你能不能修 bug」 |

**一个反直觉的判断**：这个项目最值钱的资产（口径纪律 + 可推翻的判决 + 覆盖率诚实）
**恰好是 DA 岗最稀缺、也最难伪造的能力**，但它现在被埋在最深的技术文档里，
用最不容易被 HR 和业务面试官理解的词写着。

## 三、补充设计：四个产物包

原则：**每个包直接对应一类岗位的一句话**。包 1–3 共用一个数据底座，不重复建设。

### 包 1 · SQL 语义层 + 指标字典（打通 DS/DA 与数据开发）

| 项 | 内容 |
|---|---|
| **现有原料** | `data/processed/*/*.jsonl`、`verdict.jsonl`、`data/reports/*.json`（全是单机文件，零 SQL） |
| **要做** | ① DuckDB 在 jsonl/parquet 上建**四层视图**：`raw`（原始样本）→ `stg`（清洗后 + 判决书联表）→ `marts`（按模态 × 算子 × 时间聚合）→ `metrics`（指标层）<br>② `docs/metrics.yaml`：每个指标的**名称 / 业务定义 / 计算口径 / 分母 / 来源表 / owner / 版本**<br>③ `mmc sql "..."` 与 `mmc metrics` 两个 CLI 入口<br>④ 把指标口径纳入现有的校验机制（与 `verify_claims.py` 同源，**顺带把腐烂高发的「测试基线」也锁进去**） |
| **对标** | 数仓分层（ODS-DWD-DWS-ADS）**只做最小映射**——不假装有真实业务指标，只证明「分层怎么落、口径怎么控」 |
| **验收** | 一条 SQL 能从原始 jsonl 走到指标；改动指标口径但忘了改字典 → 校验器 exit 1 |
| **工时** | 小（单模块 + YAML + 校验器，无新依赖：DuckDB 单文件） |

**简历句**：「用 SQL 建了 4 层数据模型，把 4 个模态的原始数据加工成 N 个核心指标，
指标口径由 CI 校验，防止口径漂移。」

### 包 2 · 数据质量记分卡 + SLO 告警（打通数据治理 / 数据平台）

| 项 | 内容 |
|---|---|
| **现有原料** | 每算子 P/R、**已评覆盖率**、**适用性标记**（`ALL_UNSCORED` / `LOW_COVERAGE`）、PSI 漂移、数据 CI 门禁 |
| **要做** | ① 把四类质量维度（完整性 / 准确性 / 一致性 / 时效性）映射到现有算子，形成**质量维度 → 算子 → 分数**的台账<br>② `configs/quality_slo.yaml`：每个数据集 × 维度的**目标线**，破线即红<br>③ 记分卡页面：单资产健康度 + 破线项 + 归因（复用已有的预计算 JSON 与 Streamlit 门户）<br>④ 一条命令导出的「数据质量报告」（对标 GX Data Docs 的产物形态） |
| **差异化（必须写进产出物）** | **把「未评覆盖率」做成一等公民**：覆盖率 0% 的算子，它的 0% 不是「零召回」而是「没有分母」。<br>**行业主流工具在这块是盲区**（GX 只报 pass/fail，不报「这条规则今天有没有评过」）——这是本项目能碾压的诚实度 |
| **验收** | 给定数据集，输出健康度分数 + 破线项 + 逐项归因；人为劣化后分数下降、SLO 变红 |
| **工时** | 小~中（复用 `real_sensor_interactive.json` 那套预计算与前端） |

**简历句**：「为 29 条数据质量规则建立 P/R 与覆盖率台账，输出数据质量记分卡与 SLO 告警，
劣化可自动发现并归因到具体规则。」

### 包 3 · 血缘图 + 数据契约（打通数据治理 / 数据平台）

| 项 | 内容 |
|---|---|
| **现有原料** | `verdict.jsonl` schema v1 已有 **PROV-O 三元组** + `input_fingerprint` + 人审回填位 |
| **要做** | ① 把三元组渲染成**字段级血缘图**（源指纹 → 算子 → 判决 → 输出），命名对齐 **OpenLineage** 语义以提高行业可读性<br>② `contracts/*.yaml`：每个数据集的 **schema + 版本 + 校验规则**，落盘并进 CI<br>③ 影响分析：改一个算子 / 一个 schema → 列出受影响的下游 |
| **对标** | OpenLineage + Marquez 的最小语义子集（**不做完整实现**） |
| **验收** | schema 破坏性变更 → 契约校验失败；血缘图能回答「这个输出是谁产生的、用了哪条规则」 |
| **工时** | 中 |

**简历句**：「实现字段级数据血缘追踪与数据契约校验，支持影响分析，
破坏性 schema 变更在 CI 阶段阻断。」

### 包 4 · 一份 DS 口味的分析报告（零代码，收益最高）

| 项 | 内容 |
|---|---|
| **现有原料** | R@1 0.459→0.556（+21%）、随机删 baseline 净贡献 +0.131、去重组 ΔR@1 -0.017、分层采样 +24%、剂量-响应曲线 |
| **要做** | 按 DS 岗报告结构重写一份**分析报告**（不是工程报告）：<br>业务问题 → 指标选择与口径理由 → 方法与对照设计 → 结果 → 稳健性与局限 → **建议** |
| **为什么值得** | **零代码，但面试时最有用**——DA 岗面试考的就是「你能不能把数据讲成结论」。现在的文档全是工程口吻，业务面试官读三行就读不下去 |
| **验收** | 给非技术读者看，能读懂「做了什么、得出什么、建议什么、哪里不确定」 |
| **工时** | 小（半天） |

**简历句**：「独立完成清洗策略效果分析报告，量化下游检索 R@1 提升 21%，
并用随机删对照组证明收益来自清洗本身而非数据量。」

## 四、明确不做（防炫技）

| 不做 | 理由 |
|---|---|
| 完整数仓分层（ODS-DWD-DWS-ADS 全套 + 维度建模 + SCD） | **没有真实业务指标**，硬做出来是模型练习，不是数据工作；面试官一问业务含义就穿 |
| 接 BI 工具（Tableau / Power BI / 帆软） | 环境成本高、演示即可替代（Streamlit / 静态 HTML 等价）；JD 里是加分项不是门槛 |
| OpenLineage / Marquez 完整实现 | 成本远超收益；只做**语义对齐**即可借用行业词汇 |
| 实时流（Flink / Kafka） | 与项目定位（离线质量）无关 |
| Spark / Deequ | 本机无环境（`ray` 已有，别再加一套） |
| 元数据平台部署（DataHub / OpenMetadata 起来跑） | 那是运维一个平台，不是证明我会做数据工作 |

## 五、JD 可写性测试：补完之后能写出什么

这是本篇的**最终验收标准**——四条都写不出，说明补的东西没打中。

1. 「用 SQL（DuckDB）建了 4 层数据模型，把 4 个模态的原始数据加工成 N 个核心指标，
   **指标口径由 CI 校验，防止口径漂移**。」
2. 「为 29 条数据质量规则建立 P/R 与覆盖率台账，输出**数据质量记分卡与 SLO 告警**，
   劣化自动发现并归因到具体规则。」
3. 「实现**字段级数据血缘追踪与数据契约校验**，支持影响分析，破坏性变更 CI 阶段阻断。」
4. 「独立完成**清洗策略效果分析报告**，量化下游 R@1 提升 21%，
   并用随机删对照组证明收益来自清洗本身。」

每条都能直接对上 JD 里的一句话：

| 我的句子 | 对上的 JD 原话 |
|---|---|
| 1 | 「统一数据口径」「熟练掌握 SQL（硬性要求）」「完成数仓分层」 |
| 2 | 「落地数据质量规则（完整性/准确性/一致性/时效性），配置告警，推动闭环」 |
| 3 | 「分析数据血缘关系，支持数据溯源、影响分析」 |
| 4 | 「输出分析报告」「实验效果评估、归因分析」 |

## 六、投递时的一句话定位

**投 DS/DA**：
> 「我不是做模型的人，我是**让数据可被信任**的人——我能定口径、建质量监控、
> 用 SQL 把数据讲成结论，而且我能证明我说的每条质量规则在真实数据上真的灵。」

**投数据平台 / 治理**：
> 「我做过一条完整的数据质量链路：从质量规则的定义、召回误杀评估，
> 到覆盖率台账、SLO 告警、血缘追踪，并且用**人为劣化注入**证明过这套门禁真的会红。」

两句话都指向同一件事：**这个项目证明的不是「我会写算子」，是「我会管数据的可信度」。**
