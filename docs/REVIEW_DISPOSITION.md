## 1. Q4 误合并 28.6%：已完成诊断，两份评审的建议都指向了错的修法

两份评审都建议「先诊断」，也都建议**调高阈值**（评审 B 明确说"调到 0.75-0.8"）。
我跑了诊断，结论是**调阈值是错的修法**。

### 1.1 第一轮：级联诊断（本机真实新闻语料 2280 篇）

`scripts/diag_dedup_cascade.py` → `data/reports/dedup_cascade_diagnosis.json`

| 指标 | 实测值 | 含义 |
|---|---|---|
| 簇总数 / 被合并样本 | 2246 / 68 | 合并率 **2.98%** |
| **最大簇** | **2** | ⭐ **没有任何级联迹象** |
| 簇大小分布 | `{1: 2212, 2: 34}` | **全部是 2 元簇**，无 3 元以上 |
| >100 的簇 | **0 个** | 与「模板化大簇」假设矛盾 |
| **桥接率** | **0.0%**（0/32 条边） | ⭐ **传递闭包级联确认不成立** |
| 跳桶次数 | 0 | — |

**这一轮直接否掉了两份评审的核心假设。** 评审 B 说"主因是 Union-Find 传递闭包级联"，
并建议"合并前检查新样本与簇内平均相似度，阻断传递链"。实测：**32 条合并边全部是
与簇代表直接相似（100%），桥接 0 条**。级联不是原因。

### 1.2 第二轮：阈值区的估计误差（这才是原因）

`scripts/diag_minhash_threshold_error.py` → `data/reports/minhash_threshold_band_error.json`

真实新闻语料**几乎没有天然近重复对**（4 万次随机采样的最高真实 Jaccard 仅 **0.18**），
所以阈值区的误差在真实数据上测不出来 —— 这是语料性质，必须受控注入才能测。
用原文层面的字符扰动构造 2000 对已知真值的样本，**只取真值 0.55–0.95 的决策相关区**（515 对）：

| num_perm | 偏差中位 | 偏差 p95 | **阈值 0.70 误判率** | 阈值 0.75 误判率 |
|---|---|---|---|---|
| **80（当前）** | 0.0343 | 0.1060 | **14.8%** | 10.7% |
| 160 | 0.0243 | 0.0718 | 10.9% | 8.7% |
| 320 | 0.0178 | 0.0488 | **7.0%** | 5.4% |

**num_perm 80→320 使误判率降53%（14.8% → 7.0%）。**

**这改变了修法**：阈值 0.75 和 0.80 的误判率（10.7% / 更低）**都低于**
把 `num_perm` 加到 160 的收益（10.9%）。也就是说：

> **同等误判率下，「加签名位数」比「抬阈值」更划算**，而且抬阈值会同时损失真重复召回。

两份评审建议的「调高阈值到 0.75-0.8」是**用召回换精确**，而真正的杠杆在 `num_perm`。

⚠️ 但要注意 7.0% 也不低 —— 判读要克制：去重是**单向丢弃**，14.8% 的候选对误判率
不等于 14.8% 的误杀率（同一簇内多条边合并后，样本级误杀率要低得多）。
**本轮不下「误杀率」的结论**，只能说「估计误差是已确认的贡献因素，调阈值不是最优解」。

### 1.3 修正后的建议（替代两份评审的「调阈值」）

1. **`num_perm` 80 → 160**（误判率 −26%，签名长度翻倍，耗时可控）
2. **把 num_perm 扫描做成常规报告**，别再拍单一值
3. 阈值维持 0.70，等误差降下来后重跑基准再看召回/误杀的真实取舍
4. 28.6% 那条数字本身**来源未明**（`text_dedup_benchmark.json` 的 `non_injected_merged`
   用的是与本轮不同的语料与注入方案）—— **需先核对它是什么再谈**（见 §4 待决）

### 1.4 ⚠️ 本轮踩的装置错误（值得留档）

诊断脚本第一版给出「阈值 0.70 误判率 **62.6%**，且 num_perm 320 完全无效（62.6%→62.6%）」。
这个结果太反常 → 查因：

- 真值算在**保留的 shingle 集合**上（得 0.73）
- 估计算在**把 shingle 用 latin-1 重建的文本**上（`shingles()` 得 0.0021）
- **两者不是同一个对象** → 真值与估计压根在比不同的东西

修正为「原文层面扰动、真值与估计同走 `shingles`/`_signature` 函数族」后才得到可信数。

**判据：若某项改进（加 num_perm 4 倍）完全不改变结果，先怀疑装置，别急着改被测对象。**
这正是本项目记忆里那条「变异没被拦住先怀疑装置」的同族 —— 记忆里的教训是
「装置错了让后一条继承前一条落盘状态」，这次是「判据的输入不是被测对象的输入」。

## 2. Q2：两份评审互相矛盾，我暂不动手

| | 主张 |
|---|---|
| **评审 A** | **不要**加通用 DSL。「配置里可以给规则参数，但不要做通用表达式引擎，否则校验、版本、测试都会失控」。只把 `keep()` 升级为返回 `Decision(keep, reason, rule_id, evidence)` |
| **评审 B** | 给 `BatchOperator` 加 `rule_expression` 支持**简单 DSL 表达式（沙箱执行）** |

两者互斥。我的判断：**评审 A 对，评审 B 的落地方案要现在做**。理由不是保守，
而是有具体成本：

**「沙箱执行表达式」在当前架构下没有宿主。** 协议层是 `Operator`/`BatchOperator`
两个类 + `min`/`max` 两个参数，引入表达式需要同时处理：表达式解析器、
沙箱（防注入）、版本化、配置 schema 校验、错误归因到具体规则、单测。
**这是一个新子系统，不是一个字段。**

评审 A 提的 `Decision` 通道是**纯收益**：不改判定的表达力（复杂逻辑仍在批量算子里），
但让「为什么这么判」变成结构化数据，可审计、可回归、可给 `StageStat` 统计。

**本轮处置**：只做 `Decision`，不做 DSL。如果后续 Q7 的时序路径真的需要规则配置，
到时再引入，并且**先在时序算子里验证一个具体用例**，不要为假想需求建引擎。

⚠️ 另外两份评审都没注意到的：`OperatorMeta` 是 `@dataclass(frozen=True)`，
加字段是可行且向后兼容的（默认 `None`）—— 这条支撑了 Q1 的改法可行性。

## 3. Q1：评审的改法**在代码里不成立**，我给出可落地的替代

两份评审都建议加指纹，都写了类似：

```python
meta[f"score_meta:{op}"] = {
    "input_fingerprint": sample.content_hash(),  # ← 这个方法不存在
    ...
}
```

**核实结果**：`Sample`（`packages/curation-eval/src/curation_eval/schema.py`）只有
`id` / `text` / `image_path` / `modality` / `meta` / `labels` 六个字段，
**没有 `content_hash()` 方法**。所以照抄这段会 `AttributeError`。

### 3.1 我的替代方案（更小、更准）

不需要引入 `content_hash` 抽象，因为**误用场景本来就少且可判定**：

```python
# meta 侧多写两个键，不新增字段、不改 Sample 结构
sample.meta[f"score:{op.name}"] = score
sample.meta[f"score_prov:{op.name}"] = op.fingerprint()   # 类级算一次，非样本级

#复用前校验（消费侧唯一改动点）
def reuse_ok(s: Sample, op: Operator) -> bool:
    return s.meta.get(f"score_prov:{op.name}") == op.fingerprint()
```

`op.fingerprint()` = `(算子源码哈希, params 排序后元组)`，**类级缓存**，零per-sample 成本。

**为什么不做样本内容哈希**：
- 样本内容变了却复用旧分数，真实场景是「同一批id 重跑且正文被替换」
- 这个场景的正确解法不是哈希失效，而是**不许复用**（见下）
- 加了哈希就要为它写失效测试，成本高于收益

### 3.2 「默认重算，显式声明可复用」

两份评审都提到这条方向，但都没说清**现在其实是反过来的**：

> `runner.py` 的注释说「换阈值重跑时，昂贵算子（CLIP 编码等）的分数可直接复用」——
> 这句话本身是**危险的默认值**，因为它没区分「换阈值」和「换算子实现」。

改为：**默认重算**，漏斗配置里显式声明哪些算子允许复用分数（只有 CLIP/perplexity
这类昂贵且实现稳定的值得），且复用必须过 `fingerprint` 校验。

⚠️ 这里有个项目特有的便利：**已有 30 个算子，当前没有任何代码路径真的复用分数**
（`runner.py` 每次都全量跑）。所以这**不是修一个 bug，是给一个不存在的优化加防护**——
我会在实现时先确认这一点，避免为一个假问题写一堆代码。

## 4. 采纳但不立刻动手的（Q3 / Q5 / Q6 / Q7 / Q8）

### Q3：None 假绿门禁 —— **判据要改，不能一刀切**

两份评审都建议加 None 率告警，且都给了阈值（评审 A：5% 告警 / 20% fail-fast；
评审 B：类似）。**方向对，但一刀切会误伤。**

本项目 `keep()` 对 `None` 返回 True 是**有意的设计**（源码注释：「无法计分 → 保留，
不误杀」）。合法的 `None` 来源至少三类：

1. 模态不匹配（`run_batch_mixed_modality` 里单独计 `skipped`，**不是 None**）
2. 输入字段缺失（如图片算 CLIP 时 `image_path` 为空）
3. 第三方库异常被吞（`perplexity` 遇超长文本、CLIP 遇损坏图片）

第2、3 类都是真实存在的。所以判据必须分状态：

```
error_rate > 0        → fail-fast（算子内部异常不该被吞）
not_applicable_rate   → 记录 + 抽检（合法缺失）
missing_input_rate > X → 告警（可能是数据源问题，但不该让整批失败）
```

⚠️ 更重要的一点：**真正的危险不是 None 率高，而是「None 率和历史基线突然不同」**。
所以 `StageStat` 该记的是 None 的**绝对值 + 分因**，门禁该比的是**基线漂移**。

### Q5：不做分布式去重 —— **完全采纳，并补充一条**

两份评审一致、且与我实测一致：当前规模不做纯分布式去重。

**补充他们都没提的一点**：混合架构（三段式：并行清洗 → 集中去重 → 并行后处理）
的前提是**签名计算能在清洗阶段顺带完成**。而当前实现里签名计算**绑在去重算子内部**
（`dedup_texts` 里 `sigs = np.stack([_signature(s.text, ...) for s in samples])`），
清洗阶段拿不到签名。

所以混合架构的**真正前置条件是拆开签名计算**，不是改传输格式。这个改动比改传输小得多，
且立刻可测（签名单独跑一遍耗时 vs 现状）。建议顺序：

1. 拆签名计算（`compute_signatures()` 独立可测）
2. 三段式编排（集中去重只传 id + 签名）
3. 传输格式换列式（这条**最后做**，因为前两步后数据量已经很小）

评审 B 说「先解决 Ray 数据传输问题」并说「大概率百万级以上反超单机」——
**这个预测我没有验证能力，不采纳为结论**。第 1、2 步做完就能实测，不需要猜。

### Q6：显式 `register_all()` —— 采纳，成本最低

实测确认：不 import 时 `available_operator_metas()` 返回 `{}`，
且 `available_operator_metas()` **没有任何空值提示**（源码就一句
`return {n: m for n, (_, m) in _REGISTRY.items()}`）。

两份评审的建议一致且正确。这条**改动最小、收益最直接**，建议作为第一个动手项。
（注意 `config.py` 里的报错「引用了未注册算子」也该补一句「是否忘了 import / register_all」。）

### Q7：时序模态独立路径 —— 采纳方向，**先确认一件事再动手**

两份评审都说得比我清楚（评审 B 的「双范式架构」提法尤其好）：
漏斗的「样本独立」假设与时序数据的「强上下文依赖」不匹配，
应按设备/时间窗分区流式计算，漏斗只做统一判决与报告层。

**但我没有动手，因为缺一个前置判断**：工业传感器是不是这个项目的核心业务。
如果只是为了让「多模态」这个说法成立而加的模态，那更划算的做法是**标记为实验性**
甚至移出主漏斗，而不是为它建一整套双范式架构。这个问题只有你能回答。

### Q8：合成 1→N —— 采纳

两份评审一致，与 ROADMAP 认定的「唯一真缺口」一致，且都指出了同一个关键歧义：
**1→N 会让漏斗的 `n_in` 语义失效**。评审 B 给的拆法（`raw_input_count` /
`processed_sample_count`）可以直接用。

补充一条两份评审都没提的：合成样本与源样本**必然高相似**（否则合成失败），
所以去重算子对合成样本的策略不能照搬 —— 要么跳过，要么标记为「合成组内去重」。
这个必须写进协议，否则会出现「合成样本被自己生成的重复洗掉」。
