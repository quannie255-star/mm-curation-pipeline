# V6 战略定位：全链路完整 + 一处极深

> 2026-09-20。起因：用户提出「算力/硬件妥协，其余全链路对标业界顶尖，
> 或直接在业界管道上做修改；否则项目没有存在意义；要符合 STAR 原则」。
> 本文是我的判断，**包含反对意见**。事实依据见 `docs/INDUSTRY_BENCHMARK.md`。

---

## 零、我的判断（三句话）

1. **你的方向对了一半**：「架构要完整对标业界」是对的，**但「完整」本身不产生价值**——
   在算力妥协的前提下做全链路对标，产物只会是「每个环节都比业界差一点的复制品」。
2. **另一半是陷阱**：「直接在业界清洗管道上做修改」如果指 **fork**，那是自毁——
   你会去维护别人的 200+ 算子，而业界 2026-08 已经给了更好的入口：**插件**。
3. **真正的答案你已经找到了，只是在考虑放弃它**：V3 ι/κ/λ 对标后的结论是
   「curation-eval『回答算子好不好』生态位成立」。**这个生态位是对的，而且没人占。**
   现在要做的是**用全链路把这个生态位撑起来**，不是放弃它去做 Data-Juicer 的低配版。

## 一、你对在哪里，陷阱在哪里

### 1.1 对的部分

| 你的判断 | 我的评价 |
|---|---|
| 算力/硬件可以妥协 | ✅ 完全同意，而且**需要妥协的比你以为的少**（见 §三） |
| 架构要完整对标业界 | ✅ 对——**缺层会让整条链不可信**（缺抽取层已经害你吃过 #65） |
| 「个人使用者没必要」 | ✅ 对。这个平台对个人太重（torch+faiss+Ray+Airflow），而个人最省事那条路业界有更成熟的工具 |
| 「业界用不到这种 toy」 | ⚠️ **部分对，但理由不对**。业界用不到是因为**规模不对**，不是质量不对。而这个理由**同样适用于 fork 方案**——你 fork 了 Data-Juicer，业界还是用不到 |
| 「单纯展现技术没必要」 | ⚠️ **一半对**。展现**实现力**没必要（AI 能复现）；展现**判断力**有价值（见 §二） |

### 1.2 陷阱：完整 ≠ 有价值

假设你花 6 个月补齐全链路。面试官看到的是什么？

> 「哦，你重新实现了 trafilatura 的抽取 + MinHash 去重 + fastText 质量分类 +
> Argilla 式的标注 UI + Croissant 元数据。**每一项都有更成熟的现成项目。**」

**这是最坏的结局**：投入最大，差异化最小。因为「完整」是可以被穷举的，
而**可以被穷举的东西没有护城河**。

### 1.3 陷阱：fork 别人的管道

「直接在业界清洗管道上做一定自己的修改」——如果指 fork：

- Data-Juicer 有 **200+ 算子**，fork 意味着你要跟上游同步 200 个算子的变更；
- 你改的那一小部分，会被淹没在别人的代码库里，**面试官看到的是「改了别人的代码」**；
- 你的评测资产（curation-eval）反而被绑死在一个实现上，失去「可评测任何框架」的立场。

**正确做法见 §五：作为插件接入，不是 fork。**

## 二、一个必须先接受的事实：AI 时代的护城河是判断，不是实现

你说「本身项目也是 ai 做的，所以单纯展现技术已经没必要」。这个自我认知很清醒，
**但结论要反过来**：

> **AI 能实现任何环节。所以「我实现了 X」的护城河是零。
> 唯一不可被 AI 复制的，是「我决定不做 X，因为 Y」——因为 AI 没有你的约束和你的品味。**

推论，直接改变项目的重心：

| 不值钱 | 值钱 |
|---|---|
| 我又写了 30 个算子 | 我证明了其中 12 个在真实分布上是净负收益，**所以砍掉** |
| 我接上了抽取层 | 我发现抽取层的某个缺陷会让下游算子产生 778 条误杀，**所以加了这一级** |
| 我实现了阈值自动调优 | 我证明了业界通用的阈值在 3 个真实域上误杀 16~28%，**所以阈值必须从分布推** |
| 支持 5 种模态 | 我明确划出第 6 种模态**不该接**，因为它没有可用的负样本 |

**你的项目已经有一批这种资产，只是你没把它们当卖点**：
PROOF_CHAIN §九 的十条自认局限、明确的「不做」清单（Next.js 真前端 / W&B / 算子市场）、
δ 判官的阴性结果（κ≈0 判不合格）、λ SemDeDup 的诚实阴性。
**这些不是欠账，是护城河。**

## 三、算力妥协的真实边界（好消息：只有 3 件事需要妥协）

我逐层盘了业界完整链路的每一层，看它是否真的需要算力：

| 层 | 需要重型算力吗 | 说明 |
|---|---|---|
| 源接入（WARC/PDF/arXiv） | ❌ 纯 CPU | 下载 + 解析 |
| **抽取层**（HTML→正文） | ❌ **纯 CPU** | trafilatura / resiliparse 都是 CPU 库 |
| 归一化层 | ❌ 纯 CPU | 编码/空白/换行——**#65 就死在这里** |
| 打分层（规则） | ❌ 纯 CPU | 你已有 |
| 打分层（**模型分类器**） | ⚠️ 小 | fastText 是 CPU 级；DeBERTa 单卡可跑 |
| 去重（exact/near） | ❌ 纯 CPU | MinHash-LSH 你已有 |
| 去重（semantic） | ⚠️ 小 | 单卡 embedding + faiss，你已有 |
| **人审层** | ❌ 纯 CPU | 只需要一个队列 + UI |
| **配比层**（manifest + ledger） | ❌ 纯 CPU | 是工程不是算力 |
| **血缘/元数据**（Croissant） | ❌ 纯 CPU | 生成 JSON-LD |
| **下游评测**（小模型裁判） | ⚠️ 小 | 0.5B–1.5B 你已在 8GB 上跑通 LoRA |
| 执行层 checkpointing | ❌ 纯 CPU | 是工程 |
| —— 绝对规模（10¹² tokens） | ✅ **需妥协** | 物理不可及 |
| —— 训练级裁判（7B / 53 任务） | ✅ **需妥协** | 物理不可及 |
| —— GPU 加速内核（cuDF/cuGraph） | ✅ **需妥协** | 物理不可及 |

**结论：全链路对标在算力上基本可行。** 你不需要妥协「架构完整」，
只需要在「绝对规模」和「训练级裁判规模」两处如实声明降级。

## 五、关键抉择：不要 fork，要插件

**这是本文最重要的一条技术建议。**

事实（2026-08-07 发布）：**Data-Juicer v1.5.5 新增 External OP Plugins——
第三方算子可以作为独立 pip 包分发，通过 Python entry points 自动注册。**

这意味着一条比 fork 好得多的路：

| | fork Data-Juicer | **作为插件接入** |
|---|---|---|
| 维护成本 | 跟上游同步 200+ 算子 | 只维护你自己的包 |
| 面试官看到 | 「改了别人的代码」 | **「我的算子能在业界框架里跑」** |
| 你的评测资产 | 被绑死在一个实现上 | **保持「可评测任何框架」的中立立场** |
| 生态位 | 变成 Data-Juicer 的分支 | **成为它的评测层 + 扩展层** |

**而且这形成闭环**（我认为这是整个战略里最漂亮的一环）：

```
        ┌───────────────────────────────────────────────┐
        │  curation-eval（你的包）                        │
        │  ＝ 回答「这个算子净收益是正是负」的评测层         │
        └───────────────────────────────────────────────┘
                    ▲                        │
        评测          │                        │ 你的算子作为插件接过去
                    │                        ▼
        ┌───────────────────────────────────────────────┐
        │  Data-Juicer / NeMo Curator（业界框架）          │
        │  ＝ 200+ 算子的执行层，但**不回答哪个算子该留**    │
        └───────────────────────────────────────────────┘
```

**为什么这个生态位是真空的**：Data-Juicer 有 200+ 算子，但**不回答「哪个算子净收益为正」**；
NeMo Curator 有 30+ 过滤器，但**不告诉你阈值该定多少**。
业界所有框架都在**扩充算子**，没有人做**判决算子**。

V3 ι/κ/λ 你自己得出的结论就是这个。**别放弃它。**

## 六、我建议的形态：全链路完整 + 一处极深

```
┌──────────────────────────────────────────────────────────────┐
│  全链路完整（补齐 10 层，如实声明规模降级）                       │
│  —— 目的：让链条可信，让任一层都能被追问                        │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│        一处极深：可审计的清洗决策（Auditable Curation）          │
│                                                              │
│   ① 判决书    每条被删样本 = 一条机器可读的裁决记录              │
│   ② 校准阈值   阈值从数据分布 + 误杀预算反推，不是拍脑袋          │
│   ③ 迁移代价   量化「合成标定的阈值在真实分布上衰减多少」          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**为什么是这三根支柱**（每一根都对着业界已知但未解决的问题）：

| 支柱 | 业界的现状 | 为什么是真空 |
|---|---|---|
| **① 判决书** | fastText/DeBERTa 分类器打分 → 删掉，**不知道为什么删**；Croissant 的 PROV-O 做到数据集/文件级，**没有落到单条记录级** | 清洗结果不可审计，下游无法追问「这条为什么被删」 |
| **② 校准阈值** | FineWeb 的 fastText 0.65、DCLM 的 top-10%——**全是启发式拍的**；「为什么是这个数」业界答不上来 | 阈值是数据管线里最脆弱的一环，且没有方法论 |
| **③ 迁移代价** | 所有人都知道合成/代理标定会衰减，**没有人公开量化过** | 这是合成评测的信任基础问题 |

**三根支柱的共同点（为什么适合你）**：

- **不需要算力**——②③ 是统计，① 是数据结构
- **全部建立在你已有的资产上**：污染器 + `labels.dirty` + `dropped_by`（①的雏形）、
  `threshold_scan` + 劣化注入（②的雏形）、三份真实数据集报告（③的雏形）
- **结果可验证**——每根都能给出前后对比数字
- **直接对齐业界标准**——①就是 Croissant 1.1 的记录级血缘，§八的门面问题顺手解决
- **护城河是判断不是实现**——这三个都是「业界知道有问题但没解决」的地方

## 七、STAR 重构：你的问题不在 A，在 S 和 R

你现在的叙事：

| | 现状 | 评价 |
|---|---|---|
| **S** 情景 | 「我造了一个数据集，注入了 10 类脏数据，然后清洗它」 | ❌ **S 是虚构的**。这是最大的问题 |
| **T** 任务 | 「建一个清洗管道」 | ⚠️ 泛，没说清约束 |
| **A** 行动 | 29 算子 / 4 模态 / Ray / 微调判官 | ✅ 这条其实很强（你想补的就是这里） |
| **R** 结果 | R@1 +21%、ppl +7.5%、κ +0.560 | ⚠️ **不可比**——119 条 held_out、单 seed，且没有对照业界 |

**核心问题：你的 A 已经很满了，S 才是空的。** 你可能在解决错误的问题。

### 重构后的 STAR

> **S（情景）**：LLM 数据清洗管线里，阈值和判据几乎全是启发式拍定的
> （FineWeb 的 `fastText ≥ 0.65`、DCLM 的 `top 10%`、C4/Gopher 的默认门限）。
> 这些阈值在代理数据上标定，**迁到真实分布后表现如何，行业没有公开量化过**。
> 我手上有三个真实工业数据集，实测发现：合成语料上 100% 召回 / 1.23% 误杀的算子，
> 迁到真实分布后**召回掉到 24~72%、误杀涨到 16~28%**，且调参无解（8σ 时误杀仍 27%、召回只剩 34.5%）。
>
> **T（任务）**：在个人算力约束下（单机 8GB），把清洗链路补到业界完整形态，
> 并解决上面这个「阈值不可信」的问题——让**清洗决策可审计、阈值可从数据推导、
> 迁移代价可预测**。
>
> **A（行动）**：
> ① 补齐 10 层链路（抽取/归一化/人审/配比/血缘），并在规模上如实声明降级；
> ② 实现判决书（每条删除的可审计裁决，对齐 Croissant PROV-O 记录级血缘）；
> ③ 阈值校准：由域分布 + 误杀预算反推，替代启发式拍定；
> ④ 迁移代价量化：给出「合成标定 → 真实分布」的预期衰减区间；
> ⑤ 算子作为插件接入 Data-Juicer，**并用自己的评测层反过来评测业界算子**。
>
> **R（结果）**：
> ① 三个真实数据集上误杀从 16~28% 降到 X%（**这是最硬的一个数**）；
> ② 每条删除可审计、可追溯到判据与输入指纹；
> ③ 给出迁移代价的可预测区间（如「±Y pp」），并指出哪些判据可迁移、哪些必须重标定；
> ④ 用同一套评测口径跑 Data-Juicer 的算子，产出公开可比的算子排名。

**这个 STAR 的 S 是真的、R 是可比的。** 而 A 比你现在计划的更聚焦——
因为你不需要「实现全链路」，你需要「用全链路支撑一个真问题」。

## 八、三阶段落地路线

### 阶段 1（先做，收益最大）：让结果可比
- 扩 held_out（119 → 千条级）、多 seed、加置信区间
- 接一个公开基准（哪怕 DCLM 的 400M-1x 档）作为外部锚点
- **目标**：让「数据好」与「噪声」在统计上可分
- **不做**：任何新算子、任何新模态

### 阶段 2（核心差异化）：三根支柱
- **① 判决书**：`verdict.jsonl`——每条判决带 `op / score / threshold / 判据依据 / 输入指纹 / 是否人工复核`
- **② 校准阈值**：`threshold_scan` → 「分布 + 误杀预算 → 阈值」的推导流程，并在三个真实域做对照
  （猜的阈值 vs 推的阈值，误杀降多少）
- **③ 迁移代价**：把已有的三份报告做成方法论——合成标定值的预期衰减区间
- **目标**：产出可对外讲的 R（那个「16~28% → X%」）

### 阶段 3（补链条 + 对齐标准）：全链路完整
- 抽取层 + 归一化层（**并用 #65 那个 bug 回头验证它真被解决了**）
- 人审层（最小面：review queue + 裁决回写，不要做完整标注系统）
- 配比层（轻量：manifest + ledger，**不做 RegMix 的代理训练**——那需要算力）
- Croissant 1.1 元数据输出（PROV-O 血缘 + DUO/ODRL 许可）
- 算子作为 pip 插件接入 Data-Juicer（external OP plugins 机制）

## 九、风险与明确不做

### 风险
1. **摊薄风险**（最大）：全链路补齐容易变成「每层都做一半」。**纪律：阶段 1-2 没出数字，不进阶段 3。**
2. **抽取层的坑很深**：编码、模板、PDF、阅读顺序——**不要试图超过 trafilatura**。
   目标是「接进来 + 证明它解决了 #65」，不是「做得比业界好」。
3. **人审 UI 是无底洞**：只做 review queue 的最小面。业界对标物是 Argilla，**不要重造它**。
4. **模型裁判的规模天花板**：0.5B–1.5B 能给的信号有限。**如实声明，不要伪装成 7B 级结论。**

### 明确不做（并且把「不做」写进文档——这是资产）
- ❌ 绝对规模的追赶（10¹² tokens）
- ❌ 训练级裁判规模（7B / 53 任务）
- ❌ GPU 加速内核（cuDF/cuGraph）
- ❌ fork 任何业界框架
- ❌ 重造 Argilla / Lilac
- ❌ 鉴权 / 多租户（没有用户之前不谈这些）
- ❌ RegMix 式配比代理训练（需要算力，且不是你的差异化）

## 十、一句话收尾

> **不要做「更完整的 Data-Juicer」。做「Data-Juicer 缺的那一层」——
> 那个回答「这个算子该不该留、阈值该定多少、删得对不对」的层。
> 全链路是为它服务的，不是目的。**
