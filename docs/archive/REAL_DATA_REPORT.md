## 零点五、真实数据的坑（都是实测出来的，不看文档）

1. **SKAB 官方 README 与文件不符**：README 写列名 `RateRMS` + 逗号分隔，**实测是
   `Volume Flow RateRMS` + 分号分隔**。照 README 写解析 → 整列 KeyError。
2. **MetroPT-3 采样率，UCI 页面自相矛盾**：页面同时写 "0.1Hz" 和 "logged at 1Hz"。
   **实测中位间隔 10 秒 ≈ 0.1Hz**（且间隔不规则，存在 12 秒的行）→ 1Hz 是错的。
   按 1Hz 算，「256 读数窗」的时长会从 42.7 分钟错成 4.3 分钟，**窗口语义整体偏掉**。
   已改为**从时间戳实测采样率**（`_sampling_hz()`），不再照文档硬编码。
3. **同一数据集目录下混着不同口径的文件**：`Group_14_Clean_Data.csv` 只有 59,445 行
   （分组子集），与全量 `labelled_df.csv`（1,516,948 行）放一起会被重复计数 →
   接入脚本改为**显式优先选全量文件**。
4. **GitHub raw / codeload 当前完全不通**；`ghfast.top` 代理实测 ~300KB/s 可用，
   `cdn.jsdelivr.net` 可用但**大文件会返回 200 + 0 字节**（别只看状态码）。
   SKAB 并行下载会随机 `[Errno 2]` 假失败，**串行重试即全过**。

## 一、SKAB：默认配置下算子**全部静默**

窗口 256（与合成语料 `WINDOW_SECONDS = 256` 用的是同一个常量）→ 1048 条样本
（干净 536 / 真实异常 512）：

| 算子 | 扔 | 误杀 | 命中真实脏窗 |
|---|---|---|---|
| `sensor_stuck` / `sensor_range` / `sensor_drift` / `unit_consistency` / `fault_vs_maintenance` | 0 | 0 | 0 |

**漏斗保留率 100%，真实脏命中 0/512。** 不误杀是好事，但一个脏窗都没抓。

根因都是「判据照着合成形态写的，真实数据里那个形态不存在」：

| 算子 | 合成判据 | 真实数据为何静默 |
|---|---|---|
| `sensor_stuck` | 窗内极差 **≤1e-9**（完美平坦） | 真实传感器永远有噪声，**不可能完美平坦** |
| `sensor_range` | 查内嵌 `RANGE_TABLE[device_type, channel]` | 真实通道/设备类型表里没有 → 走「表外不越权评判」恒 1.0（**保护正确，效果空转**） |
| `sensor_drift` | 同组需 **>5 窗**建基线 | 真实单次实验太短，每通道只有 2~4 窗 → 建不出基线 |
| `unit_consistency` | 同测点单位混源 | 单位是从数据集文档**统一填**的，无混源 → 恒过 |
| `fault_vs_maintenance` | **-999 哨兵**静默窗 | 真实数据无缺失值、无哨兵 → 恒过 |

窗口压到 64 / 步长 64（4512 条：干净 2520 / 异常 1992）后 `sensor_drift` 才启动：

| | 真实（SKAB, 窗 64） | 合成轨对照 |
|---|---|---|
| 真实脏召回 | **24.0%**（479/1992） | 100%（3 seeds 最差） |
| 真实干净误杀 | **24.5%**（617/2520） | 1.23%（3 seeds 最差） |
| precision | 43.7% | — |

**误杀不是启动瞬态能解释的**：误杀窗在组内时间位次覆盖 0~15，峰值在 5~7（紧接基线窗），
但位次 ≥9 的仍占 **23.7%（146/617）**。**也不是调阈值能救的**（探针口径，同口径横向对比）：

| 基线/阈值约定 | 召回 | 误杀 |
|---|---|---|
| 现状：最早 5 窗 + 4σ | 45.9% | 34.2% |
| 跳过前 2 窗（避开启动瞬态） | 43.4% | 33.1% |
| 跳过前 4 窗 | 43.4% | 40.5% |
| 跳过前 2 窗 + **6σ** | 38.9% | 25.3% |
| 跳过前 4 窗 + **8σ** | 34.5% | 27.4% |

放宽到 8σ 才把误杀压到 27%，召回掉到 34.5%——**没有任何阈值能救回可用区间**。
根因在模型假设：`sensor_drift` 假设「单一稳态基线 + 窗均值按固定 σ 倍偏离」，
而真实工况的**合法**波动本身就超过合成平稳过程的 σ。

## 二、MetroPT-3：标签可信但极稀疏，**无标签 ≠ 干净**

### 2.1 标签交叉验证（先说可信度）

官方失败表推导出的社区标签 `Airleak`，与官方 4 段故障窗口**逐行完全吻合**：
29,954 行有标签 = 29,954 行在官方窗口内（100%）；**3 个计划检修时刻附近全标 0**
（合法静默没被误标为故障）——**标签本身可信**。

同时暴露一个规模差异：**真实故障只占 1.97%**（29,954/1,516,948），
而合成污染器注入率是 **30%**——**差 15 倍**。合成的类别平衡是人为的。

### 2.2 算子表现（窗 256 ≈ 42.7 分钟，41,478 条：干净 40,659 / 故障 819）

| 算子 | 扔 | 误杀 | 命中真脏 | precision | 真实误杀率 |
|---|---|---|---|---|---|
| `sensor_stuck` | 1337 | **1337** | 0 | 0.0% | 3.22% |
| `sensor_range` | 0 | 0 | 0 | — | 0.00% |
| `sensor_drift` | 12339 | 11749 | **590** | 4.8% | **28.33%** |
| `unit_consistency` / `fault_vs_maintenance` | 0 | 0 | 0 | — | 0.00% |

- `sensor_drift`：真实故障召回 **72.0%**（590/819），但误杀 **28.33%**（11749/40659）；
- 漏斗端到端：41478 → 28384，**保留 68.4%**（真实数据上直接丢掉三分之一）。

### 2.3 关键发现：那 1337 个"误杀"其实抓到了真实缺陷

`sensor_stuck` 的 1337 次丢弃 **100% 是"误杀"**（官方标签里没有）。人工抽检后发现：

- 这些窗在 **7 个通道上同时完全恒定**（同一批 191 个时间点 × 7 通道）；
- 合并成 **7 段连续区间，合计约 163 小时**（占 213 天全期的 **3.19%**），
  最长一段 **61.6 小时**，全部通道数值一动不动；
- **全部落在官方故障窗口之外**。

结论有两层：

1. 这大概率是**真实的数据链路冻结**（记录仪重复输出最后一行），属于真实缺陷——
   `sensor_stuck` 抓它是对的，只是**数据集的标签体系不覆盖这类缺陷**；
2. 因此 **真实数据上「无标签 ≠ 干净」，误杀率只能是上界**，必须人工抽检才能定论。
   这正好复刻并强化了工程笔记 #65 的方法论。

## 三、C-MAPSS FD001：**"恒定"有两种完全不同的含义**

（提醒：C-MAPSS 是 NASA 动力学模型的**仿真**数据，不是真实采集数据；
此处当"结构更接近真实工业时序"的第三个靶子。）

29,757 条窗样本（干净 25,557 / 退化段 4,200，退化占 14.1%）：

| 算子 | 扔 | 误杀 | 命中真脏 | precision | 真实误杀率 |
|---|---|---|---|---|---|
| `sensor_stuck` | 9153 | 7817 | 1336 | 14.6% | **26.27%** |
| `sensor_drift` | 7035 | 4846 | **2189** | 31.1% | 16.29% |

漏斗 29757 → 13746，**保留 46.2%**。

**误杀根因查清了**：`sensor_stuck` 的 7817 次误杀里 **7220 条（92.4%）**落在
**6 个"整条轨迹恒定"的通道**上——`s1 / s5 / s10 / s16 / s18 / s19`，
在 **100/100 台发动机**上全程不变（C-MAPSS 的知名无信息列）。

> 于是同一个形态有两种相反含义：**「完美平坦」既可能是传感器卡死（故障），
> 也可能是该传感器本来就不测量任何东西（无信息通道，正常）**。
> 现有算子只看得见单个窗，没有全量上下文，**必然搞混**。

## 四、跨数据集横向结论

| 数据集 | 默认窗（256 / 30 周期） | 真脏占 | 真实表现 | 合成轨自称 |
|---|---|---|---|---|
| SKAB | 5 算子**全静默**，0 命中 | 48.9% | 压到窗 64 后：召回 **24.0%** / 误杀 **24.5%** | 100% / 1.23% |
| MetroPT-3 | drift 启动、stuck 全误杀 | **1.97%** | drift 召回 **72.0%** / 误杀 **28.3%**；stuck 1337 次全为未标签缺陷 | 100% / 1.23% |
| C-MAPSS | stuck 大面积误杀 | 14.1% | drift 召回 **52.1%** / 误杀 **16.3%**；stuck 误杀 92.4% 来自无信息通道 | 100% / 1.23% |

五条横向结论：

1. **判据是对着合成形态写的**：`≤1e-9` 平坦、`-999` 哨兵、内嵌量程表、单位字段——
   真实数据里这些形态要么不存在，要么含义不同。默认窗下算子直接空转。
2. **窗口/采样单位是隐藏的关键超参**：同一份数据，窗 256 与窗 64 的结果从"全静默"
   变成"召回 24% 误杀 24%"。而采样率必须**从时间戳实测**（UCI 页面自己写错了 10 倍）。
3. **阈值完全不可迁移**：三个数据集上，drift 的真实误杀都在 16%~28%，
   而合成是 1.23%。**这不是调参问题，是模型假设问题**。
4. **无标签 ≠ 干净**：MetroPT-3 的 163 小时全通道冻结段被官方标签漏掉，
   使"误杀率"变成上界——**真实轨必须带人工抽检环节**。
5. **同形态多含义**：C-MAPSS 的 92.4% 误杀来自无信息通道；真实数据的判别
   需要**全量上下文**（该通道是不是一直不变），单窗视角注定出错。

## 五、行动建议（按性价比）

1. **先对齐「判据 ↔ 真实形态」，别急着调阈值**：
   - `sensor_stuck`：判据从「极差 ≤1e-9」改成「变化率低于该通道噪声底」，
     并加**全量上下文**——该通道在全数据集上是否一直不变（是则属无信息通道，不判卡死）；
     同时把「合法空闲窗」豁免从 `operating_mode` 改为可用的业务信号
     （MetroPT-3 有 `COMP` 等数字量可表达运行/停机，属业务上下文，算子在样本流里读得到）。
   - `sensor_range`：量程表接真实通道（数据集文档有量纲）；**表外通道应记
     `None`（无法计分）而不是 1.0**，否则空转会被报告伪装成"通过"。
   - `fault_vs_maintenance`：静默判据从「-999 哨兵」改成「**采样停摆/心跳缺失**」——
     真实链路故障表现为"没有数据"，不是一条哨兵值。
   - `unit_consistency`：真实数据的单位在元数据里而不在样本里，需要显式注入才能测。
2. **`sensor_drift` 的模型假设要换**：单稳态基线 + 固定 σ → 工况分段基线或
   变点检测（SKAB 自带 `changepoint`、MetroPT-3 有检修台账，都可当外部监督验证）。
3. **接入脚本暴露 `--window` / `--stride` 说明**：真实数据集的 run 长度普遍短于
   合成的 256×6，窗口应由该数据集的单 run 长度反推；采样率一律实测。
4. **合成污染器要补"真实形态"注入**：噪声平坦（flakiness）、**采样停摆**、
   无信息通道（恒定但合法）、以及**真实的低脏率（~2%）**——否则合成门禁永远测不到
   上面这四类，且注入率 30% 与真实 1.97% 的差距会让阈值严重乐观。
5. **真实轨必须配抽检工具**：误杀清单要能一键导出「通道 + 时间 + 读数极值」供人工裁决
   （本轮是靠临时脚本查出来的，应固化成评测脚本的一个 section）。
6. **数字口径**：本轮结果**不进 `claims.json`**（真实轨判据还要改，未到可锁定状态）；
   等判据对齐后，按 PROOF_CHAIN §七 格式**新增「真实轨」行**，明确标注数据来源与分母。

## 七、清洗质量到底怎么样：真实背景上的**半合成注入**评测（2026-09-22，R11）

### 7.1 为什么必须自己造真值

上面 §一~§六 的所有「召回」都在回答一个错的问题。三个数据集的标签
（C-MAPSS `degraded` / MetroPT-3 `fault_window_air_leak` / SKAB `sensor_anomaly`）
**全是过程/设备异常**，没有一个提供「数据质量缺陷」真值 ——
拿它们当分母，等于**用数据质量检测器去考故障诊断**。所以真实轨那个
「C-MAPSS 21.9%」**不是能力指标**（详见 `ENGINEERING_NOTES.md` #71）。

要真的知道「洗得怎么样」，只有一条业界标准路子：**把已知缺陷注入真实录波**，
得到**有效真值**（CWRU / SKAB / MIMII 都这么做）。

### 7.2 方法与三口径（不许混）

`scripts/eval_real_injection.py`：基线跑（真实语料原样）→ 注入跑（注入已知缺陷）
→ **差分**。

| 量 | 定义 | 能不能对外讲 |
|---|---|---|
| `recall_injected` | 注入窗被丢 / 注入窗总数 | ✅ **有效真值** |
| `collateral_false_drop` | 注入跑里新丢的**非注入**窗 | ✅ 应 ≈ 0 |
| `background_flag_rate` | 基线跑丢的非注入窗占比 | ⚠️ 这份数据**自带**的异常率上界，**不是误杀率** |

**只注入数据质量型五形态**（卡死 / 校准偏移 / 越出包络 / 单位混用 / 链路静默），
刻意不注入过程异常 —— 那不在本项目职责内，注进去才是自己骗自己。

### 7.3 结果（三数据集完整档，注入率 10%、seed 42）

### 7.4 `sensor_range` 从**空转**到真的在判（R8）

§六 已如实记下：`sensor_range` 在三个真实数据集上**一次都没评过**
（通道全在手册量程表外 → 记 `None`）→ 注入 1888 条已知越界缺陷，召回 **0.0%**。
**问题不在阈值，在缺输入。**

`scripts/build_envelopes.py` 从**参考段**（每组最早 30% 窗）按
`中位数 ± 6 × 1.4826×MAD` 定**读数级**边界，跨设备/工况取**并集**，带 `n_ref`：

| 数据集 | 无包络 | 有包络 | 已评覆盖率 | 附带误丢 |
|---|---|---|---|---|
| C-MAPSS | 0.0%（`ALL_UNSCORED`） | **35.1%** | 67% | 0 |
| MetroPT-3 | 0.0%（`ALL_UNSCORED`） | **25.2%** | 43%（`LOW_COVERAGE`） | 0 |
| SKAB w64 | 0.0%（`ALL_UNSCORED`） | **43.5%** | 100% | 0 |

### 7.5 一处设计**被 MetroPT-3 推翻**（最重要的负面结果）

上面那套配方在 C-MAPSS / SKAB 上包络自身的背景异常率只有 1.16% / 0.66%，
但在 **MetroPT-3** 上是 **54.40%**（漏斗级 56.29%）—— **一半以上的真实数据被判成脏**。

根因：固定参考段隐含 **「数据稳态」这个未声明的假设**。MetroPT-3 是真实压缩机，
负载与启停在持续变化；前两个数据集（仿真退化 / 小试验台）**掩盖**了这个问题 ——
这正是「一个默认值吃遍所有数据集」的典型失败方式。

**修法**：给生成端加**留出集自检**（边界仍只由参考段拟合，用参考段之外的读数做
接受/拒绝检验；越界率 > 5% 的组**整条边界不写入**，宁可记未评）。
MetroPT-3 的 `Motor_current` 留出集越界率 **48.9% → 该组被拒**：
包络背景率 **54.40% → 0.43%**，同时漏斗注入召回 **81.2% → 89.9%**。

### 7.6 口径提醒（新增两条）

- **报召回必须同时报已评覆盖率**（R10）。一个覆盖率 0% 的算子，
  它的 `0.0%` 不是零召回，是**没有分母**。报告现已在超额时标 `<<< 召回不可引用`。
- 包络是**代理边界**，不是物理量程：只能发现「偏离自身历史形态」的值，
  发现不了「一直在量程外但稳定」的值（那种要靠手册量程）。
  **同一个 margin 不能跨数据集搬运**（MetroPT-3 就是反例）。

```bash
python -X utf8 scripts/eval_real_injection.py --source cmapss
python -X utf8 scripts/eval_real_injection.py --source cmapss --envelope /tmp/env_cmapss.json
```

## 八、误杀清单的人工裁决（2026-10-07）：把「误杀率」拆成两个数

前七节所有「误杀率」都带着同一句免责声明：**真实数据无标签≠ 干净，所以误杀率是上界**。
这句话一直成立，但它**不可操作** —— 面试时被追问「那到底误杀了多少真东西」，
唯一的答案是「不知道，要人工看」。本节把这个「不知道」变成一个可复跑的量化拆分。

### 8.1 三数据集重跑（`funnel_industrial_real.yaml`，全量）

| 数据集 | 样本 | 真实干净 | 真实脏 | 漏斗存活 | 保留率 | 干净误杀 | 漏斗误杀率 | 命中真脏 |
|---|---|---|---|---|---|---|---|---|
| SKAB | 1048 | 536 | 512 | 1037 | 99.0% | 1 | **0.19%** | 10/512 |
| C-MAPSS | 29757 | 25557 | 4200 | 28031 | 94.2% | 807 | **3.16%** | 919/4200 |
| MetroPT-3 | 41478 | 40659 | 819 | 38968 | 93.9% | 1863 | **4.58%** | 647/819 |

> C-MAPSS 的「真实脏」标签是 `degraded`（仿真退化），不是真故障 —— 读数退化本身就是
> 仿真注入的，所以这个数据集的召回天然偏高；跨数据集比召回是无意义的，只比误杀结构。

### 8.2 关键一步：按读数形态把「误杀」分成两类

`--export-kills` 导出每条丢弃记录（通道 / 时间 / 分数 / 判据代号 / 读数极值与 σ）。
判据纪律（记忆里那条「真实无标签≠干净」）在这里落地成一条**可计算**的规则：

- **硬证据 = 窗内读数极差严格 = 0**（传感器完全卡死，任何「正常工况」都不可能产生）；
- **软证据 = σ < 1e-9**（浮点噪声级，读数在数值上不动）。

落在这两类的「误杀」，**不是误杀，是数据集标签没覆盖的真实缺陷**。

| 数据集 | 数据集标干净的丢弃 | ├硬证据（极差=0） | ├软证据 | └待人工裁决 | 硬证据占全部干净窗 |
|---|---|---|---|---|---|
| SKAB | 1 | 0 | 0 | 1 | 0.00% |
| C-MAPSS | 938 | **629** | 0 | 309 | **2.46%** |
| MetroPT-3 | 2424 | **222** | 0 | 2202 | **0.55%** |

硬证据的通道分布（说明这是成片的通道级缺陷，不是零散的边界个案）：

- **C-MAPSS**：`fd003/s10` 304 条、`fd001/s6` 178 条、`fd003/s6` 147 条
  —— σ 中位数 **1e-16~1e-14**（浮点噪声），即这三个通道有**整段完全不动的读数**。
  C-MAPSS 是仿真数据，「标签说它健康」只说明**仿真器**说它健康，不说明**原始物理量**在动。
- **MetroPT-3**：`TP2` / `H1` / `Motor_current` 各 72 条（**恰好等于窗 256 × 某一常数**，
  呈整块同步形态）+ `Oil_temperature` 6 条。这与 §2.3 记录的「1337 条真实冻结」同源，
  是官方标签**系统性漏掉**的冻结段。

**所以「误杀率」这个数字的正确读法是两条**：
「MetroPT-3 误杀 4.58%」= 真实误杀 **4.58% − 0.55%（硬证据）≈ 4.03% 上界**，
外加 222 条已确认为算子抓对的真实冻结。**报 4.58% 不报 4.03% 是保守的、可以接受的口径；
把 629 条 C-MAPSS 硬证据算成「误杀 2.46%」则是明确的错误归因。**

### 8.3 尺度口径对照实验：换`scale` 会发生什么（唯一变量）

MetroPT-3 同一份语料、同一套标签、同一张算子链，**只改 `sensor_drift` 的尺度口径**
（真实档 MAD ↔ 合成门禁档 pooled）：

| 臂 | 漏斗存活 | 丢弃 | 干净误杀 | 命中真脏 |
|---|---|---|---|---|
| 真实档（MAD） | 38968 | 2510 | **1863** | 647 |
| 合成档（pooled） | 28975 | 12503 | **11845** | 658 |
| 差 | −9993 | +9993 | **+9982（6.4×）** | **+11（+1.7%）** |

**多杀 9982 条窗，只换来 11 条真脏命中。** 这是本项目「阈值有依据」这句话在真实数据上
第一次有量化落点：MAD 尺度不是调参调出来的偏好，它在真实背景上以 1.7% 的召回增益
换掉了 6.4 倍的误杀。**反过来也说明合成轨标定的那套 pooled 尺度不可搬运** ——
与 §7.5 是同一类失败的两种表现。

### 8.4 「空转」在本节的三个确认

三个数据集的 `judge_applicability` 一致显示：`fault_vs_maintenance` 与
`unit_consistency` 的目标形态命中数均为 **0** → **无适用性（空转）**。
它们报的「0 误杀」不是「检查通过」，是**一次都没评过**（SKAB/C-MAPSS/MetroPT-3 均如此，
只有 C-MAPSS 的 `sensor_stuck` 因仿真退化产生了 9153 个目标窗才真正适用）。
`sensor_range` 在三个数据集上未评窗分别为 1048 / 29757 / 41475 = **全部样本**，
因为真实数据的通道/设备类型表外 → 按设计恒1.0（保护正确，效果空转）。

**这四条规则（`sensor_range`、`fault_vs_maintenance`、`unit_consistency`，
以及 SKAB 上的 `sensor_stuck` / `sensor_drift`）在真实数据上基本没有可用靶子。**
这是「合成轨的门禁绿灯」与「真实轨的实际效用」之间最诚实的一张对照表。

**复现**：

```bash
python -X utf8 scripts/eval_real_sensor.py --source skab     --export-kills data/reports/real_skab_kills.csv
python -X utf8 scripts/eval_real_sensor.py --source cmapss   --export-kills data/reports/real_cmapss_kills.csv
python -X utf8 scripts/eval_real_sensor.py --source metropt3 --export-kills data/reports/real_metropt3_kills.csv
# §8.3 对照臂（只改 --config）
python -X utf8 scripts/eval_real_sensor.py --source metropt3 --config configs/funnel_industrial.yaml \
  --out /tmp/ab_metropt3_synth.json
```

> ⚠️ 本节数字**不进 `claims.json`**（真实轨判据仍在演进，见 `HONESTY_NOTE` 第 3 条）。
> 它们由 `data/reports/real_*.json` 与 `real_*_kills.csv` 现算，**不靠文档手抄对齐**。


## 九、真实图像数据集（COCO 2014原样）的清洗效果与归因（2026-10-08，A 步）

前八节都在时序/ 文本语料上工作，且都带一个说不清的负担：**真实数据集的标签是
「设备故障」，不是「数据质量缺陷」**，拿它当召回分母等于用质检器考故障诊断
（`eval_real_injection.py` docstring 记录了这个实测结论）。

本节换一条路：**拿真实数据集的原样 + 业界标准任务**来证明，全程**不注入任何东西**。

### 9.1 协议：为什么它不受「自己造题」的质疑

| 设计 | 取值 | 为什么这样 |
|---|---|---|
| 数据集 | COCO 2014，**1620 张原样** | 业界公开数据集，一字未改 |
| 任务 | 文本→图像检索 | COCO/COCO-CN 的标准任务，不是本项目发明的 |
| 查询 | 每张图的**官方 caption** | ground truth 由数据集自带 → **无需任何人工标注** |
| 编码 | Chinese-CLIP 512维，一次性算完并缓存 | **零重编码纪律**：换臂只换保留集合，GPU 抖动不会混进「清洗效果」 |

对比已有那张 `dirty_raw → clean_v2` 的合成对照（Recall@1 0.459 → 0.556）：那张
是**注入了486 条人工脏数据**的。本节的数据里一行脏数据都没加。

### 9.2 四臂结果（`scripts/eval_real_coco_evidence.py`，全量 1620 条）

| 臂 | 库规模 | R@1 | R@5 | R@10 | MRR |
|---|---|---|---|---|---|
| `raw_real` 真实原样 | 1620 | 0.546 | 0.815 | 0.890 | 0.666 |
| `cleaned_real` 过漏斗 | 1585 | **0.558** | 0.825 | 0.901 | 0.677 |
| `random_drop` 随机删同样数量（最差/10 seed） | 1585 | 0.547 | — | — | — |
| `random_drop` 随机删（均值） | 1585 | 0.549 | — | — | — |

**净贡献 = 0.558 − 0.547 = +0.0107**（R@1，对随机删的最差 seed）。

### 9.3 归因：+1.07pp 是从哪来的，以及它有多站得住

35 条丢弃按「是否可人工核对」拆开（判据见脚本 `classify_kills`）：

| 算子 | 丢弃 | 硬事实 | 待裁决 | 判读 |
|---|---|---|---|---|
| `semantic_dedup` | 14 | **1** | 13 | 图像向量近重复；丢的多是「同场景不同帧」（斑马群/草原） |
| `minhash_lsh` | 11 | 5 | 6 | 文本近重复，部分 caption 表述近似 |
| `phash_near` | 5 | 1 | 4 | 图像感知近重复，同上 |
| `clip_alignment` | 4 | 0 | 4 | 对齐分 0.327~0.377 < 阈值 0.38 |
| `aspect_ratio` | 1 | 0 | 1 | 长宽比 0.17，极端长条 |
| **合计** | **35** | **7（20%）** | **28（80%）** | |

**「硬事实」的唯一定义：该样本的文本与库中另一条逐字节相同**（`一间干净整洁的客厅。`
出现 2 次、`一个男人在网球场上打网球` 出现 3 次等5 组共 6 条冗余）。这是可人工核对的事实。
除此之外的都依赖模型判断 → 一律记「待裁决」，**不计入清洗有效的证据**。

由此得到三个必须一起讲的结论：

1. **真实 COCO 自带的文本冗余只有 6/1620 = 0.37%**，而漏斗丢弃 35/1620 = **2.16%**
   —— 丢弃量是真实冗余量的 **5.6 倍**。
2. **`semantic_dedup` 是过度清洗的主要来源**：14 条里只有 1 条是硬事实，其余是
   「同场景不同帧」。COCO 里一个场景有多张图，视觉近重复 ≠ 冗余。
3. **所以 +1.07pp 是**下界**，且不该当成「清洗有效」的强证据。**可对外说的那句是**：
   「在真实 COCO 上，清洗的净贡献为 +1.07pp（R@1），且**只20% 的丢弃能被人工核对确认**」。

### 9.4 一处必须记的方法论错误（本轮真踩）

第一次跑出来 **R@1 = 0.000、R@5 = 0.950、R@10 = 1.000**。这个模式本身就不对劲
（若模型完全不可用，R@5 不会这么高），于是逐条查rank：目标图在 `argsort` 里排第 1，
但脚本算出的 rank 是 2。根因是 `(sims >= diag)` —— **目标自己与自己的相似度必然等于
`diag`，用 `>=` 会把目标自己计入「排在前面的人数」**，再 `+1` 就多一位。

改成 `>` 后R@1= 0.790（200 条冒烟）/ 0.546（全量）。**这个 bug 的可怕之处不是报错，
是指标照常算得出来，只是全错**—— 看起来像「模型完全不可用」。与 ENGINEERING_NOTES
#93「门禁解决一致性、不解决真值性」同一族：一个安静的错判比没有判据更坏。

### 9.5 自然重复（证据二，全量实测）

真实 COCO 自带的重复（不注入）：md5 **完全重复 0 组**（COCO 没有字节相同的图），
但按图像向量 0.93 阈值有**17 对近重复、涉及 26 行**。这17 对正是 `semantic_dedup`
应该保留还是丢弃的争议区——它们是**同场景不同帧**，不是缺陷。

**复现**：

```bash
python -X utf8 scripts/eval_real_coco_evidence.py --n-seeds 10
# 产物：data/reports/real_coco_evidence.json + real_coco_evidence_kills.csv（35 行人工抽检入口）
```

> 本节数字同样**不进 `claims.json`**：它们的价值恰恰在于「证明净贡献很小」，
> 而对外数字（0.459 → 0.556）来自**合成注入轨**，两者口径不同、不许混。
> 面试时正确的说法是：「合成轨证明机制有效，真实轨证明边界在哪 —— 
> 真实干净数据上清洗的边际收益只有 1pp量级，而且 80% 的丢弃需要人工确认。」
